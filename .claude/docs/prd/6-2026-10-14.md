# 6 - Desktop: encrypted groups and chat (newcord)

**Date:** 2026-10-14
**Branch type:** Feature
**Status:** Draft

**Repository:** newcord · **Issue:** [osLeonardo/newcord#6](https://github.com/osLeonardo/newcord/issues/6) · **Milestone:** M2 · Encrypted group chat · **Branch:** `feature/6-desktop-groups-and-chat`

## Problem

After M1 the desktop app can only sign in and show who is online. The MLS module (#4) and the server's Groups and queue (#5) exist, but nothing in the app uses them. Nobody can create a **Group**, invite anyone, send or read a **Chat message**, or leave. M2's gate is a three-person Group where an offline **Member** catches up, the server holds only ciphertext, and a removed Member reads nothing new. It cannot be run.

## Solution

The main process becomes an MLS client of the server:

- On first start after the update it initialises the Device's MLS identity from the M1 key and keeps 20 **Key packages** plus a last-resort one on the server.
- It saves the MLS state blob to the local database after every operation and before sending anything (D39), with `secure_delete` on.
- It creates Groups, adds and removes Devices through commits with declared changes (D41), joins from welcomes, leaves through a removal request (D57), and handles the server's prompts automatically: accepted **Invitations**, new Devices (D56) and resyncs (D24).
- It checks every received commit against its declaration and the 10-person limit. A failing commit is applied anyway with a notice naming the sender (D71).
- It encrypts and decrypts Chat messages, stores the history locally, and confirms each delivery.

The interface gains:

- a Group list, Group creation and the Group chat (text only, never HTML)
- inviting by username, and accepting or declining Invitations
- the member list with removal, leaving, and blocking and unblocking (D57)
- notices for new Devices and rule-breaking commits

## User Stories

1. As a Member, I want to create a named Group (1–64 characters) and see it in my Group list.
2. As a Member, I want to invite someone by username and be told it was sent, without learning whether they blocked me.
3. As an invited user, I want to see pending Invitations with the Group's name and the inviter, and accept or decline each.
4. As an invited user who accepted, I want to be added automatically by whichever Member's app is online, and see the Group appear.
5. As a Member, I want to send text Chat messages and read everyone's in one order, the same on every Device.
6. As a Member, I want messages shown as plain text, so that nobody can run code or inject formatting through a message.
7. As a Member who was offline, I want every message sent while I was away to appear when I return.
8. As a Member, I want my chat history kept on my Device after the server deletes its copy (D9).
9. As a Member, I want to see who is in the Group and how many Devices each person has.
10. As a Member, I want to remove someone, which removes all their Devices, so that they cannot read anything sent afterwards.
11. As a Member, I want to leave a Group, which stops my deliveries at once and deletes the Group from my Device (D57).
12. As a Member, I want to block and unblock someone, so that their Invitations stop and their messages are hidden in Groups we share (D57).
13. As a Member, I want a notice in each shared Group when someone adds a new Device (D56), so that I can check their safety number later (M4).
14. As a Member, I want a notice naming the sender when a commit does something other than what it declared, or takes the Group past 10 people (D71).
15. As a user, I want my new Device added to my Groups automatically and to see only messages sent after it joined (D56).
16. As a Member whose Device fell out of sync, I want to be re-added automatically, losing only the messages that expired (D24).
17. As a Member, I want my Device always to have Key packages available, so that people can add it while it is offline.
18. As a Member, I want my Device's MLS state written to disk before anything leaves it, so that a crash never loses keys the Group already relies on (D39).
19. As a Member, I want deleted keys really erased from the local database (`secure_delete`).
20. As a Member, I want simultaneous changes by two Members resolved without anyone noticing: the losing app applies the winning commit and retries if still needed.
21. As the developer, I want an automated three-Device test to prove M2's gate: offline catch-up, ciphertext only on the server, and a removed Member reading nothing new.
22. As the developer, I want to confirm on Windows computers that the Group screens behave as specified.

## Implementation Decisions

### Interfaces and Contracts

- **Server:** the Envelopes, the Key package upload and the rules from #5's PRD (`.claude/docs/prd/5-2026-10-14.md`).
- **MLS:** the `@newcord/mls` API from #4's PRD (`.claude/docs/prd/4-2026-10-14.md`), called only from the main process.
- **Payloads inside MLS** are JSON with a `type`. `chat.text` carries a message ID created by the sender, the text and the time sent (`06-message-formats.md`).
- **Preload API:** named functions and subscriptions for Groups, messages, Invitations, members and blocks. Arguments are validated against shared schemas as in M1.

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Longest Chat message: 4,000 characters.** This is a new value.
2. **Message order:** messages are shown in the server's sequence order, so every Device agrees, labelled with the sender's own time.
3. **Prompts are handled automatically:** accepted Invitations, `device.new` and `resync` are handled by the app in the background with no user action, whichever Member's app gets them first.
4. **Removing someone** removes all their Devices in one commit. Leaving deletes the Group and its history from this Device.
5. **Blocking is per Account, shared across your Devices:** the server sends the Account's block list after `hello` and whenever it changes. Every Device hides messages from blocked Accounts entirely, with no placeholder. This adds one small item to #5's Step 01.
6. **Local history** is kept until you leave the Group. There's no expiry on the Device.
7. **Notices** (new Device, rule-breaking commit) appear as system lines in the chat, are stored locally and are never sent.
8. **No unread counts or notifications in M2.** Those come in M4.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D8 MLS; D9 the server deletes after delivery; D12 everyone equal; D13 Invitations by username; D17 10 people; D20 unencrypted local storage; D24 30 days and resync; D39 one state blob saved after every change; D41 declared changes checked by every app; D56 new Devices added automatically; D57 leaving and blocking; D70 credential identity; D71 apply and warn.
- Settings in `09-m2-build.md`: 20 Key packages plus one last-resort, topped up below 5; 16-byte random Group IDs; names 1–64 characters; the limit counts people.
- Security checklist, M2: Chat messages rendered as text, never HTML; the MLS state saved before anything is sent; `secure_delete` on; every commit checked (D71).

### Schema Changes

The app's local SQLite database gains:
- the MLS state blob
- Groups (ID, name)
- Chat messages (Group, sequence number, message ID, sender, text, time sent)
- notices
- pending Invitations

Blocked Accounts come from the server and are kept in memory.

## Out of Scope

- The tray, notifications, unread counts and the settings screen (M4).
- Safety numbers (M4, #11). This issue only shows the new-Device notice.
- Removing a lost Device (#7) and deleting an Account (D67).
- Calls (M3).

## Additional Notes

- Depends on #4 and #5.
- Blocking per Account needs #5 to send the block list after `hello` and on change. If approved, that line is added to #5's Step 01 acceptance criteria.
- A Chat message from a blocked Account still arrives and is decrypted, so the MLS state stays correct; it is only hidden.
- The commit check compares the declared Device IDs with the identities the commit really added and removed (D70 credentials). Parsing those identities must reject anything not shaped `<username>:<deviceId>`.

## Steps

### Step 01 — MLS identity, state and Key packages

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-17, US-18, US-19

#### What To Build

On first start after the update, the main process initialises the Device's MLS identity from its M1 Ed25519 key, username and `deviceId`. It keeps the MLS state blob in the local database, with `secure_delete` on. Every MLS operation from here on goes through one path that saves the new blob and only then sends anything to the server. The Device uploads 20 Key packages plus a last-resort one, and tops back up to 20 whenever the server reports fewer than 5. Later starts restore the state with `loadState`.

Not included: Groups (Step 02 onwards).

### Step 02 — Groups and Invitations

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-2, US-3, US-4, US-20

#### What To Build

A person can create a Group (16 random bytes as its ID, a name of 1–64 characters) and see it in the Group list, and invite someone by username. The invitee sees pending Invitations with the Group's name and the inviter, and accepts or declines each.

When an accepted Invitation reaches a Member's app, the app:
1. fetches the invitee's Key packages
2. commits the addition with a declared change
3. merges the commit once the server accepts it
4. sends a welcome to each new Device

The invitee's app joins from the welcome, and the Group appears. If the server rejects the commit because another one won the epoch, the app drops its own, applies the winning one, and retries only if the addition is still needed.

Not included: Chat messages (Step 03).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process Group, Invitation and commit handling, preload functions and subscriptions, Group list, create-Group, invite and Invitations screens, local tables, tests)

#### Acceptance Criteria

- [ ] Creating a Group with a valid name creates the MLS Group and sends `group.create`; it appears in the list; names outside 1–64 characters are refused before sending
- [ ] Inviting by username sends `invite` and shows "sent" whatever the server does with it
- [ ] The invitee's app lists pending Invitations with the Group's name and the inviter, and accept or decline sends `invite.reply`
- [ ] After an acceptance, a Member's app adds every Device of the invitee with one commit declaring exactly those Devices, merges it after acceptance, and sends each Device its welcome
- [ ] The invitee joins from the welcome and the Group appears in their list
- [ ] Two Members' apps handling the same prompt at once end with one addition: the loser clears its commit, applies the winner and does not add again
- [ ] Integration tests with two and three app instances against the real server cover each rule above
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 03 — Chat messages

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-5, US-6, US-7, US-8

#### What To Build

A Member can send a text Chat message of up to 4,000 characters to a Group. Every Member's Device decrypts it, stores it locally, sends `ack`, and shows it in the Group chat in the server's sequence order, labelled with the sender's time. Messages are always rendered as text, never as HTML. A Device that was offline receives everything waiting on `hello` and shows it in order. History stays on the Device after the server deletes its copy.

Not included: member management (Step 04), blocking (Step 06).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process encryption, decryption, storage and acknowledgement, Group chat screen, local messages table, tests), `packages/shared` (the `chat.text` Payload schema, if not already there)

#### Acceptance Criteria

- [ ] Sending encrypts a `chat.text` Payload with a fresh message ID, the text and the time sent; text over 4,000 characters is refused before sending
- [ ] Every other Member's Device shows the message with the sender's username, in sequence order, and sends `ack` after storing it
- [ ] Text containing HTML or script tags is displayed literally
- [ ] A Device offline while three messages are sent shows all three, in order, after reconnecting
- [ ] After every Device has acknowledged, the server holds no copy, and the history is still shown after an app restart
- [ ] Integration tests cover each rule above
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 04 — Members, removing and leaving

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-9, US-10, US-11

#### What To Build

The Group chat shows its members as people with their Device counts, read from the MLS state. Any Member can remove someone. One commit removes all that person's Devices with the change declared, and the removed person's app shows that they were removed. A Member can leave: the app sends the removal request, deletes the Group and its history locally, and the next Member online completes the removal. In both cases the departed person reads nothing sent afterwards.

Not included: commit checks and notices (Step 05).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process removal, leaving and pending-proposal handling, member list and actions, tests)

#### Acceptance Criteria

- [ ] The member list shows each person once with their number of Devices
- [ ] Removing someone sends one commit declaring all their Devices; after it, they cannot decrypt new messages and their app shows the Group as left
- [ ] Leaving sends the removal request, deletes the Group and its messages from the local database, and the next Member online commits the removal
- [ ] After leaving, the person receives nothing more from that Group
- [ ] Integration tests with three app instances cover each rule above
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 05 — Commit checks, new Devices and resync

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-13, US-14, US-15, US-16

#### What To Build

Every commit received is compared with its declared change and with the 10-person limit. A commit that fails is still applied, and the app shows a notice in the Group naming the sender and what the commit really did (D71). `device.new` prompts are handled automatically: a Member's app adds the new Device to each shared Group. A notice appears in each shared Group, and the new Device reads only messages sent after it joined (D56). `resync` prompts are handled automatically too: a Member's app removes and re-adds the Device in one commit, and the Device rejoins from its welcome (D24).

Not included: safety numbers (M4).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process commit check, notices, `device.new` and `resync` handling, notice display, tests)

#### Acceptance Criteria

- [ ] A commit whose real additions or removals match its declaration produces no notice
- [ ] A commit adding or removing an identity it did not declare is applied and produces a notice naming the sender and listing the real change
- [ ] A commit taking the Group past 10 people is applied and produces a notice
- [ ] Logging in a new Device for a Member leads to its automatic addition to each shared Group, a notice there, and no access to earlier messages
- [ ] A `resync` prompt leads to the Device's removal and re-addition in one commit, after which it reads new messages again
- [ ] Integration tests cover each rule above, the mismatches using a test-only way to send a misdeclared commit
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 06 — Blocking

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-12

#### What To Build

A person can block or unblock someone from the member list. The app sends `block` or `unblock`. Every one of the person's Devices receives the Account's block list from the server, after `hello` and on change, and hides messages from blocked Accounts entirely. The messages are still decrypted, so the MLS state stays correct. Invitations from a blocked person never arrive (the server's part, #5).

Not included: removing the blocked person from shared Groups. That stays a separate action (D57).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process block list, filtering, block and unblock actions, tests)

#### Acceptance Criteria

- [ ] Blocking someone hides their messages in every shared Group on all of the blocker's Devices, including messages already shown
- [ ] Unblocking shows their messages again, including those received while blocked
- [ ] Hidden messages are still decrypted and acknowledged, and the Group keeps working
- [ ] Integration tests cover each rule above
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass
