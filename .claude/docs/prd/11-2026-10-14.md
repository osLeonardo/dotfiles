## Problem

Members trust that the keys in their Groups really belong to their friends, but nothing lets them check. A **Safety number** (D45) lets two people read a 60-digit number to each other, on a Call or in person, and confirm that nobody is impersonating either of them.

## Solution

For any Member, the app computes the Safety number between you and them, the way Signal builds its 60-digit numbers. Each side contributes 30 digits from their username and all their Devices' identity keys, and the two halves are put in a fixed order so both people see the same number. It is shown as 12 blocks of 5 digits, with a button to mark the person verified. When someone's keys change (a new Device or a reinstall), every shared Group shows "<name>'s safety number changed", and the verified mark is cleared.

## User Stories

1. As a Member, I want to open a person's Safety number from the member list.
2. As a Member, I want to see exactly the same 60 digits as the other person, in 12 blocks of 5, so that we can read them to each other.
3. As a Member, I want to mark a person verified after we compare, and see that mark in the member list.
4. As a Member, I want to be told in every shared Group when someone's Safety number changes, and have their verified mark cleared.

## Implementation Decisions

### Interfaces and Contracts

- Each half is computed as in `11-m4-build.md` step 9: the username plus the sorted identity keys, hashed 5,200 times with SHA-512, and turned into 30 digits. The two halves are sorted and joined.

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Where the keys come from:** a person's Device keys are read from the MLS credentials of a Group you share (D70), not from the server's Key directory. A server that lies about keys then cannot change the number.
2. **The verified mark** is stored locally per Device, together with the Safety number it was given for. Any change to that number clears it.
3. **The change notice** builds on #6's new-Device notice: one line per shared Group when a person's set of Device keys changes.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D7 Safety numbers; D45 60-digit blocks compared aloud or in person; D56 new Devices (which change the number); D70 credential identity.

### Schema Changes

The app's local database gains verified marks: the person and the Safety number that was verified.

## Out of Scope

- Blocking or removing someone automatically when their number changes.

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-2, US-3

#### What To Build

From the member list, a person's Safety number opens as 12 blocks of 5 digits, computed from your username and Device keys and theirs. The keys are read from the MLS credentials of a Group you share. A "Mark as verified" button stores the mark with the number it was given for, and the member list shows verified people.

#### Affected repositories and layers

- newcord: `apps/desktop` (main process computation, key collection from MLS state, verified marks in the local database, preload functions, Safety number screen, member list mark, tests)

#### Acceptance Criteria

- [ ] Unit tests show the number is identical computed from either side, has 60 digits, and changes when any Device key of either person changes or a Device is added
- [ ] The keys used are those in the shared Group's MLS credentials, not the server's Key directory
- [ ] The screen shows 12 blocks of 5 digits and a verify button; verified people are marked in the member list
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass
