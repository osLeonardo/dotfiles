# 5 - Server: groups, invitations and the message queue (newcord)

**Date:** 2026-10-14
**Branch type:** Feature
**Status:** Draft

**Repository:** newcord · **Issue:** [osLeonardo/newcord#5](https://github.com/osLeonardo/newcord/issues/5) · **Milestone:** M2 · Encrypted group chat · **Branch:** `feature/5-server-groups-and-queue`

---

## Problem

After M1 the server knows Accounts and Devices but nothing about **Groups**. It cannot create a Group, deliver an **Invitation**, hand out **Key packages**, order MLS commits so every Device agrees on the next epoch, or hold encrypted messages for a Device that is offline. Without that, the MLS module (#4) and the desktop app (#6) have nothing to route through, and M2's gate — an offline Member gets everything later, while the server holds only ciphertext — cannot be reached.

## Solution

The server becomes M2's router and queue, never reading content:

- **Groups:** created with a name and a creator Device, and renamed by any **Member** (D12, D40). Membership is tracked by Device, and the 10-person limit counts people (D17).
- **Invitations:** sent by username and accepted or declined. Invitations from someone the invitee has blocked are dropped silently (D57).
- **Key packages:** uploaded in batches. Each is handed out once, except the last-resort one, and only to callers with a reason to add that Account. Each Device is told when it runs low.
- **Ordering:** for each epoch the first valid commit wins. Its declared additions and removals (D41) update membership, and every MLS message and commit gets the Group's next sequence number.
- **Queue:**
  - Every **Envelope** is stored once, with a delivery row per recipient Device. It's pushed to Devices that are online and replayed in order on `hello`.
  - Each **Delivery confirmation** deletes that Device's copy, and the message goes once nobody is waiting for it.
  - The hourly cleanup expires undelivered copies after 30 days (D24) and asks for a resync when one was a commit.
- **New Devices and leaving:** a new Device prompts a Member's app to add it (D56). A leave request stops delivery to the leaver at once (D57).
- **Narrowing:** presence and the **Key directory** now cover only Accounts that share a Group or a pending Invitation (D64).

## User Stories

1. As a Member, I want to create a named Group (1–64 characters), so that I have a place to chat.
2. As a Member, I want to rename a Group, so that the name stays meaningful; I know the server can read it (D40).
3. As a Member, I want to invite someone by username, so that they can join my Group (D13).
4. As an invited user, I want to see the Group's name and who invited me, and accept or decline, so that nobody is added without my say.
5. As an invited user who accepted, I want a Member's app to add every one of my Devices, even if no Member was online when I accepted.
6. As a user, I want Invitations from someone I blocked to be dropped without them knowing (D57).
7. As a user, I want to block and unblock someone.
8. As a Member, I want my Device's Key packages handed out only to people with a reason to add me, each package once, so that they are not harvested or reused.
9. As a Device owner, I want to be told when my Device has fewer than 5 Key packages left, so that my app tops them up.
10. As a Member, I want the server to accept only the first commit for each epoch and reject later ones, so that every Device agrees on the Group's state.
11. As a Member, I want the server to refuse a commit whose declared change would take the Group past 10 people (D17), knowing every app checks too (D41).
12. As a Member, I want every MLS message and commit numbered in one order per Group, so that every Device processes them in the same order.
13. As a Member who was offline, I want every message and commit waiting for me delivered in order when I reconnect.
14. As a Member, I want each message deleted from the server as soon as every Device that should get it has confirmed, so that nothing lingers (D9).
15. As a Member whose Device was away more than 30 days, I want the expired copies deleted. If one was a commit, I want the Group asked to re-add my Device (D24).
16. As a Member, I want a Device that someone added after its welcome to receive the welcome even if it was offline.
17. As a user who logged in a new Device, I want a Member of each of my Groups to be prompted to add it, even if they come online later (D56).
18. As a Member who leaves a Group, I want deliveries to me to stop at once, while the next Member online completes my removal (D57).
19. As a Member, I want presence only from people I share a Group with, so that strangers do not see when I am online.
20. As a user, I want the Key directory to answer only about Accounts I share a Group or a pending Invitation with (D64).
21. As the operator, I want Invitations and Key package requests rate-limited, so that nobody can spam invitations or drain Key packages.
22. As the operator, I want the database to hold only ciphertext, Group names and routing metadata, never a readable Chat message.

## Implementation Decisions

### Interfaces and Contracts

- **Envelopes** (`06-message-formats.md`), all validated against shared schemas: `group.create`, `group.rename`, `invite`, `invite.reply`, `keypackage.get`, `device.new`, `mls.commit`, `mls.proposal`, `mls.welcome`, `mls.message`, `ack`, `block`, `unblock`, `resync`, and `presence` narrowed.
- **`mls.commit`** carries the Group, the epoch it was made in, and the declared additions and removals as Device IDs (D41).
- **`ack`** names the Group and sequence number.
- **Key package upload** is an authenticated HTTP request carrying a batch (`06-message-formats.md`, "Upload key packages").

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Low Key package warning:** after `hello`, and whenever a Device's count of non-last-resort packages drops below 5, the server sends that Device a count. The upload response returns the new count.
2. **Who may request Key packages:** `keypackage.get` succeeds only for a target Account that
   - has accepted an Invitation to a Group the caller is a Member of, or
   - already shares a Group with the caller and has a Device not yet in that Group (a new Device, D56, or a resync, D24).
3. **Accepted Invitations wait for a Member:** an accepted Invitation whose Devices are not yet added is re-sent to Members as they come online, until a commit adds them. `device.new` and `resync` prompts are re-sent the same way until handled.
4. **Invitation rules:**
   - An Invitation is refused if the Group already has 10 people with Invitations counted, or if the invitee is already a Member.
   - Pending Invitations expire after 30 days, matching D24.
   - An Invitation from a blocked person is stored as never delivered, and the inviter sees it as sent.
5. **Leaving:** after a leave request, the leaving Device's Account stops receiving that Group's deliveries at once and is treated as gone for presence, while its Devices stay in the MLS Group until the removal commit.
6. **Rate limits:** **20 Invitations per hour per Account**, and **60 Key package requests per hour per Account**.
7. **A `blocks` table** (blocker, blocked) and a pending/accepted/declined/expired status on Invitations. The guide's table list in step 6 omits the first.
8. **Message size:** the 64 KiB WebSocket limit is checked against real commits and welcomes for a 10-person Group with two Devices each. If they don't fit, stop and ask for a new limit.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D9 delete after delivery; D12 everyone equal; D13 add by username with an Invitation; D17 up to 10 members; D24 30 days and resync; D40 Group names visible to the server; D41 declared changes; D56 new Devices added automatically; D57 leaving and blocking; D64 narrowed Key directory.
- Settings in `09-m2-build.md`: 16-byte Group IDs from the creator; names 1–64 characters; the 10-person limit counts people, not Devices; 20 Key packages plus one last-resort per Device.
- The hourly cleanup runs inside the server process.

### Schema Changes

New tables as in `09-m2-build.md` step 6: `groups`, `group_members`, `invitations`, `key_packages`, `messages`, `deliveries`. Two additions:
- a `blocks` table
- the Invitation status values above, including `expired`

## Out of Scope

- Anything in the desktop app (#6): checking commits, saving state, the screens.
- The MLS module itself (#4); the server never runs it (D41).
- Removing a lost Device (#7) and deleting an Account (D67).
- Call messages (M3), which travel as ordinary `mls.message` Envelopes.

## Additional Notes

- Depends on #2, which provides the socket registry, presence and Key directory to narrow. Tests can use opaque byte strings as MLS payloads. The server never parses them, so #4 is not needed to build or test this issue.
- Every rule in this issue is enforced on Device IDs and Account IDs from the verified session, never from fields the client claims about itself.

## Steps

### Step 01 — Groups, blocking and narrowed presence

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-2, US-7, US-19, US-22

#### What To Build

A Member's Device can create a Group with a 16-byte ID and a name, becoming its first Member, and any Member can rename it. A user can block and unblock another Account. Presence, which went to every connected client in M1, now goes only to Accounts that share a Group. All of M2's server tables exist from this step on.

Not included: Invitations (Step 02), Key packages (Step 03), commits and the queue (Step 04).

#### Affected repositories and layers

- newcord: `packages/shared` (Envelope schemas for `group.create`, `group.rename`, `block`, `unblock`), `apps/server` (migrations for every M2 table, Group and block handling, presence narrowing, tests)

#### Acceptance Criteria

- [ ] The tables `groups`, `group_members`, `invitations` (with statuses pending, accepted, declined, expired), `key_packages`, `messages`, `deliveries` and `blocks` are created on start
- [ ] `group.create` with a 16-byte ID and a name of 1–64 characters stores the Group at epoch 0 with the sender's Device as its only Member; a duplicate ID, a wrong-length ID or a name outside 1–64 characters is rejected
- [ ] `group.rename` by a Member updates the name and notifies the Group's online Members; by a non-Member it is rejected
- [ ] `block` and `unblock` add and remove a row for the sender's Account; blocking oneself is rejected; repeated calls are harmless
- [ ] After `hello`, and whenever it changes, every connected Device of an Account receives that Account's block list (approved with #6's PRD, so all of a person's Devices hide the same people)
- [ ] Presence snapshots and changes reach only Accounts that share at least one Group; an Account with no Groups sees nobody online
- [ ] Tests cover each rule above

#### Implementation Notes

### Step 02 — Invitations

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-3, US-4, US-6, US-20, US-21

#### What To Build

A Member can invite an Account by username to a Group. The invitee gets the Invitation, with the Group's name and the inviter's username, when online or at their next `hello`, and can accept or decline. An Invitation is refused when the Group already has 10 people, counting pending Invitations, or when the invitee is already a Member. Invitations from someone the invitee has blocked are stored as never delivered, and the inviter is told only that it was sent. Each Account can send up to 20 Invitations per hour. The Key directory now answers only about Accounts that share a Group, or a pending Invitation in either direction, with the caller (D64).

Not included: adding the accepted invitee's Devices, which needs Key packages and commits (Steps 03–05).

#### Affected repositories and layers

- newcord: `packages/shared` (`invite` and `invite.reply` schemas), `apps/server` (Invitation handling, Key directory narrowing, tests)

#### Acceptance Criteria

- [ ] `invite` by a Member to an existing username creates a pending Invitation and delivers it with the Group's name and the inviter's username, at once or at the invitee's next `hello`
- [ ] `invite` by a non-Member, to an unknown username, to a current Member, or to a Group with 10 people counting pending Invitations, is rejected
- [ ] An Invitation from a blocked inviter is never delivered, and the inviter's response is identical to a delivered one
- [ ] `invite.reply` accept or decline by the invitee sets the status; a reply by anyone else, or to a non-pending Invitation, is rejected
- [ ] The 21st Invitation sent by one Account within an hour is rejected
- [ ] The Key directory answers for Accounts sharing a Group or a pending Invitation with the caller, and returns the same "not found" as an unknown username for anyone else
- [ ] Tests cover each rule above

### Step 03 — Key packages

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-8, US-9, US-21

#### What To Build

A Device can upload a batch of Key packages over authenticated HTTP, one of them optionally last-resort. The response carries its count of ordinary Key packages left. After `hello`, and whenever that count drops below 5, the server tells the Device its count. A Member's Device can ask for Key packages of one Account with `keypackage.get`. It receives one per Device of that Account, each handed out once and deleted, except a last-resort one, which is kept and handed out only when no ordinary package is left. The request succeeds only if the target Account either has accepted an Invitation to a Group the caller is a Member of, or already shares a Group with the caller and has a Device not yet in that Group. Each Account can make up to 60 requests per hour.

Not included: using the packages in commits (Step 04).

#### Affected repositories and layers

- newcord: `packages/shared` (upload request, count and `keypackage.get` schemas), `apps/server` (upload route, counting, hand-out rules, tests)

#### Acceptance Criteria

- [ ] Uploading a batch stores the packages for the caller's Device and returns its ordinary-package count; uploading a new last-resort package replaces the previous one
- [ ] After `hello`, and whenever the count drops below 5, the Device receives its count
- [ ] `keypackage.get` for an Account that accepted an Invitation to the caller's Group returns one package per Device of that Account and deletes the ordinary ones handed out
- [ ] When a Device has no ordinary package left, its last-resort package is handed out and kept
- [ ] `keypackage.get` succeeds for a co-Member's Device that is not yet in a shared Group, and is rejected for any other target, including a co-Member whose Devices are all already in the Group
- [ ] The 61st request by one Account within an hour is rejected
- [ ] The request body limit of 64 KiB accommodates a batch of 21 packages (checked with realistically sized data)
- [ ] Tests cover each rule above

### Step 04 — Ordering and the delivery queue

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-10, US-11, US-12, US-13, US-14, US-16, US-22

#### What To Build

The server orders and queues every Group message:
- An `mls.commit` is accepted only if it was made in the Group's current epoch, and only if its declared change keeps the Group at 10 people or fewer.
- Declared additions must be Devices of an Account with an accepted Invitation to the Group, or new Devices of a current Member's Account. Declared removals must be Devices in the Group.
- An accepted commit gets the next sequence number, raises the epoch, updates `group_members` and marks those Invitations as handled. It's queued for every Member Device, including those being removed.
- A later commit for the same epoch is rejected, and its sender is told so.
- `mls.message` from a Member is queued for every other Member Device. `mls.welcome` is queued for the named Device.
- Online Devices get queued items at once. On `hello`, a Device gets everything waiting for it in sequence order.
- An `ack` deletes that Device's copy, and a message is deleted once no copies remain.

Not included: re-sent prompts, leaving and the hourly cleanup (Step 05).

#### Affected repositories and layers

- newcord: `packages/shared` (`mls.commit`, `mls.message`, `mls.welcome`, `ack` schemas), `apps/server` (ordering, membership updates, queue, replay, acknowledgements, tests)

#### Acceptance Criteria

- [ ] A commit for the current epoch with a valid declared change is accepted, given the next sequence number, raises the epoch by one and updates `group_members` to match the declaration
- [ ] A second commit for the same epoch is rejected and its sender told so; the Group's state is unchanged
- [ ] A commit whose declared change would make 11 people, that adds a Device not eligible for this Group, or that removes a Device not in it, is rejected
- [ ] An accepted commit is queued for every Device that was a Member before it, including any it removes
- [ ] `mls.message` from a Member is stored once, queued for every other Member Device, pushed at once to those online, and rejected from a non-Member
- [ ] `mls.welcome` is queued only for the Device it names, which must have been added by an accepted commit
- [ ] On `hello`, a Device receives everything queued for it in sequence order per Group
- [ ] `ack` deletes only that Device's copy; the stored message is deleted once no copies remain
- [ ] A test inspects the database after a conversation and finds payloads only as the opaque bytes sent, with no readable message text from the server's side
- [ ] Tests cover each rule above

#### Blockers

- [Step 03 — Key packages](#step-03--key-packages)

#### Implementation Notes

- Check the epoch and assign the sequence number inside one transaction, so two commits arriving together cannot both win.
- The 10-person count is of distinct Accounts whose Devices are Members after the declared change.

### Step 05 — New Devices, leaving, expiry and resync

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-5, US-15, US-17, US-18

#### What To Build

Prompts that need a Member's app to act are re-sent until someone handles them:
- **Accepted Invitations** whose Devices are not yet added.
- **`device.new`**, when a Member's Account gains a Device that is not in their Groups (D56).
- **`resync`**, for Devices that missed a commit.

Each goes to the Group's online Members, and again to Members as they connect, until a commit handles it. `mls.proposal` with a leave request stops deliveries to the leaving Account in that Group at once and removes it from presence for that Group. The request is still queued for the other Members, so the next one online can commit the removal (D57).

The hourly cleanup:
- deletes queued copies older than 30 days
- issues `resync` when an expired copy was a commit
- expires pending Invitations older than 30 days

Not included: removing a lost Device (#7).

#### Affected repositories and layers

- newcord: `packages/shared` (`device.new`, `mls.proposal`, `resync` schemas), `apps/server` (prompt tracking and re-sending, leave handling, hourly cleanup with an injectable clock, tests)

#### Acceptance Criteria

- [ ] After an invitee accepts with no Member online, the first Member to connect receives the prompt, and it stops once a commit adds the invitee's Devices
- [ ] Logging in a new Device for a Member's Account sends `device.new` to the online Members of each of their Groups, re-sent to Members as they connect until a commit adds it
- [ ] After a leave request, the leaver receives nothing more from that Group and drops out of its presence, while the request reaches the other Members
- [ ] With a simulated clock, the cleanup deletes copies older than 30 days, sends `resync` for a Device whose expired copy was a commit, and expires Invitations older than 30 days
- [ ] A `resync` prompt is re-sent to Members as they connect until a commit re-adds the Device
- [ ] Tests cover each rule above

#### Blockers

- [Step 04 — Ordering and the delivery queue](#step-04--ordering-and-the-delivery-queue)

#### Implementation Notes

- Inject the clock into the cleanup so tests can move time forward without waiting.
