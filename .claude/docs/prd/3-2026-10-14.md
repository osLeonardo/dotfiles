# 3 - Desktop: security baseline, identity and screens (newcord)

**Date:** 2026-10-14
**Branch type:** Feature
**Status:** Draft

**Repository:** newcord · **Issue:** [osLeonardo/newcord#3](https://github.com/osLeonardo/newcord/issues/3) · **Milestone:** M1 · Backend and accounts · **Branch:** `feature/3-desktop-identity-and-screens`

---

## Problem

After the scaffold (#1) the desktop app is the electron-vite template as generated. Its window runs without the sandbox, and its preload hands `ipcRenderer` to the interface, so both break the app rules in `CLAUDE.md`. It has no identity, stores nothing and cannot talk to the server (#2). A person cannot sign up, log in or see who is online, so M1's gate cannot be reached.

## Solution

The desktop app becomes a hardened Electron shell around M1's account features:

- Every window keeps context isolation and the sandbox on and Node.js off, under a strict Content Security Policy. Navigation and new windows are blocked, and links open in the browser only if they are http or https. The interface reaches the main process only through a few named preload functions whose sender and arguments are checked.
- The backend address is built into each build (D65): `http://localhost:3000` in development, `https` and `wss` only in release builds.
- On first start the main process creates the **Device**'s Ed25519 identity key and keeps it, with the tokens and the Account's username, in a local SQLite database (D20). An installation belongs to one **Account** at a time (D60).
- Screens for sign-up, the one-time **Recovery code**, login, password change, password recovery, the "online now" list and the warning before switching Accounts. All styled with Tailwind CSS (D69).
- The main process keeps the session alive by renewing the access token 1 minute before it expires and holding the WebSocket open. It returns the person to the login screen whenever the server ends the session.

## User Stories

1. As a new user, I want to sign up from the app with a username and password, so that I get an Account and this Device is logged in.
2. As a new user, I want to see my Recovery code once, in groups of four, and confirm I saved it before continuing, so that I do not lose it by clicking through.
3. As a user, I want the app to tell me why a sign-up was refused (taken username, invalid username, short password), so that I can fix it.
4. As a returning user, I want to log in with my username and password, so that this installation becomes the same Device as before (D59).
5. As a user, I want to stay logged in across app restarts without typing my password, as long as my session is valid.
6. As a user, I want to see which other Accounts are online right now, updating live, so that I know who is around.
7. As a user, I want to log out, so that this Device's session ends at once.
8. As a user on a logged-in Device, I want to change my password by typing the new one twice, without the old one (D55).
9. As a user who forgot my password, I want to recover my Account with my username and Recovery code, see my new code once, and then log in.
10. As a user typing a Recovery code, I want letter case, spaces, dashes and look-alike letters forgiven, so that a correct code is never refused for its formatting.
11. As a user, I want to be warned before I sign up or log in as a different Account on this installation, because it erases the app's local data and creates a new identity key (D60).
12. As a user who was logged out by the server (password changed elsewhere, a copied token detected, recovery used), I want the app to return to the login screen instead of failing silently.
13. As a user with a flaky network, I want the app to reconnect on its own, so that the online list comes back without restarting.
14. As a user, I want the interface never to hold my keys, tokens or network access, so that a flaw in the interface cannot leak them.
15. As a user, I want the app to refuse to load remote pages, navigate away or open new windows, and to open only http and https links in my browser.
16. As a user, I want a release build to talk to the server only over https and wss, so that nobody on the network can read or change the traffic.
17. As a user, I want the app to refuse every permission request in M1 (camera, microphone, location and the rest), so that nothing is granted before it is needed.
18. As the developer, I want the development build to reach my local server at `http://localhost:3000` with no configuration, so that I can run both side by side.
19. As the developer, I want a build that contains a non-local address that is not https or wss to fail, so that a release can never ship with an insecure address (D65).
20. As the developer, I want to confirm on two Windows computers that two Accounts see each other online and that logging one out removes it from the other's list, so that M1's gate passes.

## Implementation Decisions

### Interfaces and Contracts

- **Server:** the routes, response fields, Envelopes and close codes from #2's PRD (`.claude/docs/prd/2-2026-10-14.md`), through the schemas in `@newcord/shared`.
- **Identity key:** Ed25519, created with Node.js's built-in crypto in the main process. It is sent as the raw 32-byte public key in base64, which is what #2 accepts. The private key is stored in a form from which its raw bytes can be recovered, because OpenMLS rebuilds its credential from them in M2.
- **Preload API:** a small set of named functions for the M1 actions (sign up, log in, log out, change password, recover, read the session state, confirm the Account-switch warning) plus subscriptions to session and presence changes. `ipcRenderer` and Node.js are never exposed. The main process rejects any call that does not come from the app's own window, or whose arguments do not match their schema.
- **Local database:** one SQLite file in Electron's per-user data directory, holding the identity key pair, the Account's username, the `deviceId` and the tokens, unencrypted (D20).

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Reconnecting:** after a network drop, the WebSocket reconnects with exponential backoff, starting at 1 second and doubling up to 30 seconds. The backoff resets after a successful `hello`.
2. **Ended sessions:** a "session ended" close code, or a refused refresh, deletes the stored tokens but keeps the identity key, username and `deviceId`, and shows the login screen. Logging back in to the same Account is the same Device.
3. **What counts as a different Account (D60):** signing up, or logging in with a username other than the one stored on this installation. Both show the warning. Confirming it wipes the local database and creates a new identity key before continuing; cancelling changes nothing.
4. **Recovery code screen:** shown after sign-up and after recovery, in groups of four, with a "Continue" button that only enables after ticking "I have saved this code".
5. **Password change:** the new password is typed twice.
6. **"Online now":** lists the *other* online Accounts by username, not your own.
7. **Permissions:** every permission request is refused in M1. M3 opens the microphone and screen capture.
8. **Screens:** chosen with plain React state from the session state. No router library.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D5 Electron; D20 unencrypted local storage (an accepted risk); D21 React; D27 electron-vite; D34 better-sqlite3 in the app, rebuilt for Electron; D55 password change without the old password; D59 login sends the identity key; D60 one Account per installation; D65 built-in server address; D69 Tailwind CSS.
- The app rows of the security checklist marked M1: context isolation and sandbox on with Node.js off in every window; a strict Content Security Policy (only the app's own scripts, no remote code, no eval); a few named preload functions with sender and argument checks; no remote pages, navigation or new windows, and only http and https links opened externally.
- Settings in `08-m1-build.md`: JWT renewal 1 minute before expiry, the username and password rules, the Recovery code format and alphabet.
- Keys, tokens, the local database and all network calls live only in the main process.

### Schema Changes

A new local SQLite database in the app (not the server's), holding the identity key pair, the Account's username, the `deviceId` and the current tokens.

## Out of Scope

- Anything on the server (#2).
- Groups, chat, Key packages and MLS (M2).
- The tray, start at login, notifications and the settings screen (M4).
- Packaging, Electron fuses and automatic updates (M5).
- Showing or verifying safety numbers (M4).

## Additional Notes

- Depends on #1. The end-to-end checks need #2 running.
- `better-sqlite3` in the app must be rebuilt for Electron's Node.js version (`"postinstall": "electron-builder install-app-deps"`, `08-m1-build.md` step 8). Adding it or Tailwind CSS (`tailwindcss`, `@tailwindcss/vite`) may bring packages with install scripts. Any not already approved needs the user's approval by name.
- A sandboxed preload can only use a limited set of Electron modules; anything it needs from `@newcord/shared` must be bundled into it.
- In development, Vite injects styles inline for live reloading, so only the development build's policy may allow inline styles; the release policy does not (D69).
- `react-patterns.md`: pure logic (session handling, reconnecting, address checks, argument validation) must have tests; purely visual components need not.

## Steps

### Step 01 — Hardened shell and built-in server address

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-14, US-15, US-16, US-17, US-18, US-19

#### What To Build

The template's window becomes a hardened shell before any feature lands in it. Every window has context isolation and the sandbox on and Node.js off, and runs under a strict Content Security Policy: a release policy that allows only the app's own scripts and styles, and a development policy that additionally allows what Vite's live reloading needs. The template's preload is replaced by the app's own named API, empty of features for now, behind a main-process check of every call's sender and arguments. Navigation and new windows are blocked; http and https links open in the default browser and nothing else opens at all. Every permission request is refused. The backend address is built into each build (D65), and a build with a non-local address that is not https or wss fails. Tailwind CSS (D69) styles the window.

Not included: any account feature, the local database, the identity key (Step 02 onwards).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process window creation and security handlers, preload, renderer entry and its policy, electron-vite configuration, Tailwind setup, tests)

#### Acceptance Criteria

- [ ] Every window is created with context isolation and sandbox on and Node.js integration off; no code path creates a window otherwise
- [ ] The preload exposes only named functions through the context bridge; neither `ipcRenderer`, `@electron-toolkit/preload`'s `electronAPI` nor any Node.js module reaches the interface, and that package is no longer used
- [ ] The main process rejects an IPC call from any sender other than the app's own window, and any call whose arguments do not match its schema; both are covered by tests
- [ ] The release build's policy allows scripts and styles only from the app itself, with no `unsafe-eval` and no `unsafe-inline`; only the development build allows inline styles and the dev server connection
- [ ] Navigation away from the app and new windows are refused; an http or https link opens in the default browser, and any other scheme opens nothing; covered by tests of the link rule
- [ ] Every permission request is refused
- [ ] The backend address comes from the build: `http://localhost:3000` in development; a test shows the address check rejects a non-local `http` or `ws` address and accepts local ones and `https`/`wss`, and the build configuration runs that check
- [ ] Tailwind CSS is set up through its Vite plugin and styles the renderer
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass
- [ ] The user confirms the window still opens and renders styled content in development, and that the developer console shows no policy violations

#### Blockers

#### Implementation Notes

- A Content Security Policy in a `<meta>` tag applies to pages loaded from files as well as from the dev server; HTTP-header approaches do not reach `file://` pages in release builds. Whatever approach is used, the release policy must be the strict one.
- `tailwindcss` and `@tailwindcss/vite` are new dependencies approved by D69. If they or anything else asks to run an install script, stop and ask the user.
- Keep the address check a small pure function, so it can be tested and called from the build configuration alike.

### Step 02 — Identity, local store, sign-up, login and logout

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-2, US-3, US-4, US-5, US-7

#### What To Build

On first start the main process creates the Device's Ed25519 identity key and stores it in the app's local SQLite database. A person can sign up from the sign-up screen and sees the Recovery code screen, then lands on a logged-in home. Someone can also log in from the login screen, and a logged-in person can log out back to the login screen. Every action goes from the screen through the preload API to the main process, which calls the server (#2) and stores the username, `deviceId` and tokens. After a restart with stored tokens, the app opens logged in. Sign-up and login errors from the server are shown in words.

Not included: renewing tokens or the WebSocket (Step 03), password change and recovery (Step 04), the warning for a different Account (Step 05) — until Step 05, signing up or logging in as another username is refused with a plain message.

#### Affected repositories and layers

- newcord: `apps/desktop` (main process identity, local database, server client, session state, preload functions, sign-up, Recovery code, login and home screens, tests), `packages/shared` (only if a schema needs adding)

#### Acceptance Criteria

- [ ] `better-sqlite3` is a desktop dependency, rebuilt for Electron with `"postinstall": "electron-builder install-app-deps"`, and the app opens its database from Electron's per-user data directory
- [ ] On first start the main process creates one Ed25519 key pair and stores it; later starts reuse it; the private key never crosses the preload
- [ ] The public key is sent as its raw 32 bytes in base64, and the stored private key can be turned back into its raw bytes (a test proves both)
- [ ] Sign-up from the screen creates the Account on the server, stores the username, `deviceId` and tokens, and shows the Recovery code in groups of four
- [ ] The Recovery code screen's Continue button stays disabled until "I have saved this code" is ticked, and the code is not stored anywhere
- [ ] Login from the screen stores the returned `deviceId` and tokens; logging out and back in to the same Account returns the same `deviceId`
- [ ] Logout calls the server, deletes the stored tokens, keeps the key, username and `deviceId`, and shows the login screen
- [ ] After a restart with stored tokens, the app opens logged in without asking for the password
- [ ] A taken username, an invalid username, a short password and wrong credentials each show a clear message
- [ ] Integration tests run the main-process flows against the real server from `apps/server`, started in the test with an in-memory database, without a network port where possible
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

#### Blockers

- [Step 01 — Hardened shell and built-in server address](#step-01--hardened-shell-and-built-in-server-address)

#### Implementation Notes

- Node.js exports Ed25519 public keys as SPKI by default; the raw 32 bytes are what the server accepts (#2's PRD). The JWK form of a key holds the raw public and private bytes directly.
- Tests running under plain Node.js need `better-sqlite3` built for Node.js, while the app needs it built for Electron; keep the database behind a small interface so tests can supply their own instance, and check that `pnpm test` still runs after the Electron rebuild.
- Needs #2 merged.

### Step 03 — Live session and the online list

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-5, US-6, US-12, US-13

#### What To Build

While logged in, the main process keeps the session alive. It renews the access token 1 minute before it expires, opens the WebSocket, and sends `hello`. The home screen shows "online now", the other online Accounts by username, updating live from presence. When the connection drops, it reconnects with exponential backoff, starting at 1 second and doubling up to 30 seconds, and resets after a successful `hello`. When the server ends the session, the app deletes the stored tokens, keeps the identity key, username and `deviceId`, and shows the login screen. The session ends either through a session-ended close code or a refused refresh (a reused, expired or unknown token).

Not included: password change and recovery (Step 04).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process token renewal, WebSocket client, presence state, reconnect logic, session-ended handling, preload subscriptions, "online now" list on the home screen, tests)

#### Acceptance Criteria

- [ ] The access token is renewed 1 minute before it expires, and the new refresh token replaces the old one in the local database
- [ ] After login or a restart with a valid session, the main process opens the WebSocket and sends `hello` with the current access token
- [ ] The home screen lists the other online Accounts and updates when they come online or go offline; the person's own Account is not listed
- [ ] After a network drop the app reconnects with delays of 1, 2, 4… seconds up to 30, and the delay resets after a successful `hello` (covered by tests of the backoff logic)
- [ ] A session-ended close code, or a refused refresh, deletes the stored tokens, keeps key, username and `deviceId`, and shows the login screen; logging in again returns the same `deviceId`
- [ ] An authentication close code after an expired access token triggers a renewal and a reconnect rather than a logout
- [ ] Integration tests against the real server cover: two sessions seeing each other online, one logging out and disappearing from the other's list, and a reused refresh token returning the app to the login screen
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

#### Blockers

- [Step 02 — Identity, local store, sign-up, login and logout](#step-02--identity-local-store-sign-up-login-and-logout)

#### Implementation Notes

- Recent Node.js versions, and the one inside Electron, have a built-in WebSocket client; a library is not needed.
- Use the Envelope schemas and close codes from `@newcord/shared`, as defined in #2.

### Step 04 — Password change and recovery

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-8, US-9, US-10, US-12

#### What To Build

A logged-in person can open a password change screen, type the new password twice and save it. This Device stays logged in, and the person's other Devices return to their login screens as the server ends their sessions. From the login screen, someone who forgot their password can open recovery, enter their username, Recovery code and a new password twice, see their new Recovery code once (the Step 02 screen), and then log in. Typed codes are forgiven for letter case, spaces, dashes and look-alike letters.

Not included: changes to the server (#2).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process calls, preload functions, password change and recovery screens, tests), `packages/shared` (Recovery code normalisation, if not already there from #2)

#### Acceptance Criteria

- [ ] The password change screen requires the new password twice, refuses mismatches and passwords shorter than 12 characters before calling the server, and confirms success
- [ ] After a change, this Device stays logged in; in an integration test, a second session of the same Account returns to its login screen
- [ ] The recovery screen takes the username, the Recovery code and the new password twice; on success it shows the new code with the same confirmation as after sign-up, then the login screen
- [ ] A code typed in lower case, with spaces or dashes, or with O, I or L in place of 0 and 1 is accepted when otherwise correct (covered by tests of the normalisation)
- [ ] A wrong code shows a clear message, and the server's rate limit is shown as "too many attempts, try again later"
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

#### Blockers

- [Step 03 — Live session and the online list](#step-03--live-session-and-the-online-list)

#### Implementation Notes

- Normalise codes with the same Crockford alphabet the server uses, from `@newcord/shared`.

### Step 05 — Switching Accounts on this installation

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-11

#### What To Build

Signing up or logging in with a username other than the one stored on this installation first shows a warning. The warning explains that it erases this app's local data and creates a new identity key (D60). Confirming wipes the local database, creates a new key and continues with the sign-up or login as a new Device. Cancelling leaves everything as it was. This replaces Step 02's plain refusal.

Not included: keeping several Accounts side by side (D60 option B, not chosen).

#### Affected repositories and layers

- newcord: `apps/desktop` (main process wipe and new key, preload function to confirm, warning screen, tests)

#### Acceptance Criteria

- [ ] Signing up or logging in with the stored username proceeds with no warning
- [ ] Signing up or logging in with a different username shows the warning before anything is sent to the server
- [ ] Cancelling leaves the local database, key, username, `deviceId` and tokens unchanged
- [ ] Confirming deletes the stored tokens, key, username and `deviceId`, creates a new key pair, and then completes the sign-up or login as a new Device
- [ ] An integration test shows the new Device's identity key differs from the old one, and the server accepts it for the new Account
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

#### Blockers

- [Step 02 — Identity, local store, sign-up, login and logout](#step-02--identity-local-store-sign-up-login-and-logout)

#### Implementation Notes

- Log out of the old Account on the server before wiping, if a session exists, so its refresh token does not linger until it expires.
