## Problem

Friends cannot install the app: there is no installer, no way to get updates, and no release process. Building releases on a development laptop is also against the security checklist.

## Solution

- **Installer:** electron-builder produces a per-user NSIS installer for Windows (D73), with unused Electron fuses switched off.
- **Updates:** electron-updater checks GitHub Releases at start-up and every 6 hours, downloads in the background, and installs on the next restart, never during a Call (D29, D29b).
- **Releases:** a GitHub Actions workflow, triggered only by version tags, builds the WebAssembly module and the installer on a clean Windows runner and publishes to GitHub Releases (D48, D49) with SHA-256 checksums.
- **Account protection:** the GitHub account and `main` are protected first.

## User Stories

1. As a friend, I want a Windows installer that installs for my user without an administrator prompt.
2. As a friend, I want the app to update itself in the background and install the update when I next restart it.
3. As a friend in a Call, I want an update never to restart the app mid-Call; I want a "restart to update" offer when the Call ends.
4. As the developer, I want pushing a version tag such as `v0.1.0` to build and publish a release, and nothing else to publish one.
5. As the developer, I want releases built on a clean runner, never my laptop.
6. As a friend, I want each installer's SHA-256 listed in the release notes, so that I can check what I downloaded.
7. As the developer, I want unused Electron fuses switched off in the packaged app, so that it cannot be run as plain Node.js or debugged from the command line.
8. As the developer, I want my GitHub account and the release tags protected, because nothing else stops a fake update (D29b).

## Implementation Decisions

### Interfaces and Contracts

- `electron-builder.yml`: NSIS, `perMachine: false`, publish to GitHub; the `appId` from #12.
- Fuses: `RunAsNode`, `EnableNodeOptionsEnvironmentVariable` and `EnableNodeCliInspectArguments` off, and `OnlyLoadAppFromAsar` on, in an afterPack hook (`12-m5-build.md` step 5).

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **The workflow appends the SHA-256 checksums** to the release notes itself, instead of you doing it by hand after each release.
2. **The release workflow runs on Windows only** (D73), with Node.js 26 and the Rust toolchain for the WebAssembly module.
3. **Packaging `@<name>/mls`'s `.wasm`:** it must be unpacked from the asar archive, or loaded in a way that works inside it. The step that packages the app proves this on an installed copy.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D29, D29b unsigned automatic updates with no extra signature check; D48 GitHub Actions; D49 GitHub Releases; D73 Windows only.
- Settings in `12-m5-build.md`: semantic versioning from 0.1.0; checks at start-up and every 6 hours, never installing during a Call; tag-triggered releases; per-user NSIS; checksums in the release notes.

### Schema Changes

None.

## Out of Scope

- Code signing (D29, an accepted risk).
- Linux packages (D73).

## Steps

### Step 01 — Installer and fuses

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-1, US-7

#### What To Build

`pnpm --filter desktop build` followed by electron-builder produces a per-user NSIS installer, with the version starting at 0.1.0. An afterPack hook switches the unused Electron fuses off. The installed app runs everything from M1 to M4, including the MLS module's `.wasm` file, the local database and push-to-talk.

#### Affected repositories and layers

- newcord: `apps/desktop` (electron-builder configuration, afterPack hook, packaging of native modules and the `.wasm` file)

#### Acceptance Criteria

- [ ] The installer installs for the current user without an administrator prompt
- [ ] The packaged binary has `RunAsNode`, `EnableNodeOptionsEnvironmentVariable` and `EnableNodeCliInspectArguments` off and `OnlyLoadAppFromAsar` on (checked with `@electron/fuses`' read command)
- [ ] The user confirms that the installed app signs in, chats in a Group (MLS loads), joins a Call and uses push-to-talk

#### Blockers

#### Implementation Notes

- Needs #10, #11 and #12 merged.
- Native modules (`better-sqlite3`, `uiohook-napi`) and the `.wasm` file usually need unpacking from the asar archive.

### Step 03 — Release workflow

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-4, US-5, US-6, US-8

#### What To Build

The user first protects the GitHub account with a hardware security key or other strong two-factor authentication, and sets protection rules on `main` and on version tags. Then `.github/workflows/release.yml` runs only on `v*` tags, on a Windows runner, with every action pinned to a full commit hash and read-only permissions except for publishing. It installs Node.js 26, pnpm, Rust and the matching `wasm-bindgen-cli`, runs `pnpm install --frozen-lockfile`, builds the module and the app, publishes the installer to GitHub Releases, and appends each file's SHA-256 to the release notes.

#### Affected repositories and layers

- newcord: `.github/workflows/release.yml`
- GitHub: account security, branch and tag protection (by the user)

#### Acceptance Criteria

- [ ] The user confirms the account and the `main` and tag protections are in place
- [ ] The workflow triggers only on `v*` tags, runs on Windows, pins every action to a commit hash, and grants write access only to the publishing job
- [ ] The release notes of a published release list the SHA-256 of each installer file

- [Step 01 — Installer and fuses](#step-01--installer-and-fuses)

### Step 04 — Release gate

**Status:** Pending
**Execution type:** HITL
**Stories covered:** US-1 to US-8

#### What To Build

M5's release check: tagging `v0.1.0` publishes a release. Its installer installs and runs on a clean Windows machine. Tagging `v0.1.1` then publishes an update that the installed app downloads and installs on its next restart.

#### Affected repositories and layers

- newcord: version numbers only

#### Acceptance Criteria

- [ ] `v0.1.0` installs and runs on a clean Windows machine
- [ ] The installed `v0.1.0` updates itself to `v0.1.1` after a restart, and not during a Call
