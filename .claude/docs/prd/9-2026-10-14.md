# 9 - Desktop: voice and screen-sharing calls (newcord)

**Date:** 2026-10-14
**Branch type:** Feature
**Status:** Draft

**Repository:** newcord · **Issue:** [osLeonardo/newcord#9](https://github.com/osLeonardo/newcord/issues/9) · **Milestone:** M3 · Calls · **Branch:** `feature/9-voice-and-screen-calls`

## Problem

Groups can chat (M2) but cannot talk. Each **Group** has one drop-in **Call** (D3), and none of it exists yet:
- joining and leaving
- voice for up to 6 **Participants** in a mesh (D2)
- screen sharing (D10, D43)
- push-to-talk and a mute hotkey (D44 to D44c)
- **Hide my IP** (D14)

## Solution

The Group chat gains a Call:

- **Joining and leaving:** a Member joins or leaves with one button. `call.join` and `call.leave` travel inside MLS, so only Members know who is in the Call. Each pair of Participants connects directly with WebRTC, using perfect negotiation where the lower `deviceId` is the polite side. Offers, answers and candidates travel as MLS-encrypted `call.signal` messages (D18). Connections use the relay from #8, and Hide my IP forces it.
- **Voice:** Opus with Chromium's echo cancellation, noise suppression and automatic gain. It's sent by voice activity or push-to-talk, with push-to-talk working while a game is in front through `uiohook-napi` (D74). A global mute hotkey toggles the microphone (D44c).
- **Screen sharing:** a Participant picks a screen or window from the app's own picker. Video only (D43), sharp text over frame rate, the chosen codec first (H.264 by default, D11), and at most 1.5 Mbps per viewer. A visible indicator with a stop button shows while sharing.
- **Limits and window behaviour:** a seventh person sees "call full". Closing the window hides it during development so a call keeps running (D42), and launching the app again shows it.
- **Measurement:** CPU use per viewer is measured for each codec.

## User Stories

1. As a Member, I want to join my Group's Call with one click and leave the same way.
2. As a Member, I want to see who is in the Call and who is speaking.
3. As a Member, I want to talk with up to 5 others, each connected directly, with clear audio (echo cancellation, noise suppression, gain).
4. As a seventh person, I want to be told the Call is full instead of joining a broken Call.
5. As a Member, I want the server never to see who is in the Call or how to reach them, so that Call setup is MLS-encrypted end to end (D18).
6. As a Member behind a difficult network, I want the Call to fall back to the relay automatically.
7. As a Member, I want Hide my IP to route all my Call traffic through the relay, so that Participants never see my IP address (D14).
8. As a Member, I want to choose voice activity or push-to-talk.
9. As a gamer, I want push-to-talk to work while a game is in front (D44b, D74).
10. As a Member, I want a global hotkey to mute and unmute myself from anywhere (D44c).
11. As a Member, I want to share a screen or a window I pick in the app's own picker, without sound (D43).
12. As a viewer, I want shared text and code to stay sharp, with the frame rate dropping first.
13. As a sharer, I want a visible "you are sharing" indicator with a stop button.
14. As a Member, I want my chosen codec used for my share, falling back to another if a viewer cannot decode it (D11b).
15. As a Member in a Call, I want closing the window to hide it rather than end the Call (D42), and launching the app again to show it.
16. As the developer, I want CPU use while sharing to 1, 3 and 5 viewers measured for each codec and recorded, so that the default codec is chosen on evidence (D11).
17. As the developer, I want a 6-person Call with a screen share proven on Windows, so that M3's gate passes.

## Implementation Decisions

### Interfaces and Contracts

- **Payloads inside MLS** (`06-message-formats.md`):
  - `call.join` and `call.leave` carry only their type.
  - `call.signal` carries the recipient Device and a WebRTC offer, answer or candidate. Every Device receives it, and only the recipient acts on it.
- **Relay:** credentials come from `GET /relay/credentials` (#8). The relay addresses are built in per build (D65, #8).
- **Main process ↔ window:** the main process encrypts and decrypts every Call message and passes plain connection details to the window through named preload functions. WebRTC runs in the window (D42). The main process grants only microphone and screen-capture permissions; everything else is refused (security checklist, M3).

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Stale Call messages:** Call messages more than 60 seconds old (by the sender's time) are ignored. A Device returning from offline doesn't act on old offers. A Participant whose Device goes offline, or doesn't connect within 30 seconds, is dropped from the Participant list.
2. **The call-full rule is enforced by each app.** The server doesn't know who is in a Call. A seventh joiner sees "call full" and sends nothing.
3. **Temporary call settings in M3:** a small Call settings panel holds the microphone mode, push-to-talk key, mute hotkey, codec and Hide my IP. M4 folds these into the full settings screen (#10).
4. **Defaults:**
   - voice activity on, with a 300 ms delay before the microphone closes
   - no push-to-talk key until one is chosen
   - mute hotkey `Ctrl+Shift+M`
   - codec H.264
   - Hide my IP off (D14)
5. **Closing the window during development:** closing hides the window, and a single-instance lock makes launching the app again show it. The tray itself arrives in M4 (#10).

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D2 mesh of up to 6; D3 one drop-in Call per Group; D10 voice and screen sharing; D11 and D11b codecs, H.264 by default; D14 Hide my IP; D18 MLS-encrypted Call setup; D42 Calls in the main window; D43 screen without sound; D44 to D44c microphone modes and mute hotkey; D73 Windows only; D74 `uiohook-napi`.
- Settings in `10-m3-build.md`: 6 Participants; Chromium's voice processing; 1080p, up to 30 fps, at most 1.5 Mbps per viewer; detail over frame rate; your own relay for STUN and TURN; relay passwords valid for 1 hour.

### Schema Changes

The app's local database stores the temporary Call settings above.

## Out of Scope

- The full settings screen, tray, notifications and start at login (M4, #10).
- Webcam video (D10) and screen-share sound (D43).
- The strict-firewall test through port 443 (moved to #14 by #8).

## Additional Notes

- Depends on #6 (MLS messaging in Groups) and #8 (relay).
- `uiohook-napi` runs an install script and must be approved by name. Wrap it behind the app's own push-to-talk interface (coding rules).
- WebRTC's built-in encryption (DTLS-SRTP) protects the media itself. MLS protects the setup messages that carry each side's fingerprint, so the server cannot swap them (D18).

**Status:** Implementing

**Stories covered:** US-1, US-2, US-3, US-4, US-5, US-15

Joining sends `call.join` through MLS, and the app connects to every other Participant with one `RTCPeerConnection` per pair, using perfect negotiation with the lower `deviceId` as the polite side. ### Step 02 — Relay and Hide my IP

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-6, US-7

#### What To Build

Before connecting, the app fetches relay credentials from `GET /relay/credentials` and uses the built-in relay addresses for STUN and TURN. Connections fall back to the relay when a direct link fails. Hide my IP, a toggle in the Call settings panel from Step 03 or a temporary toggle until then, forces relay-only connections from the next Call on.

#### Affected repositories and layers

- newcord: `apps/desktop` (relay credentials, connection configuration, Hide my IP setting, tests)

#### Acceptance Criteria

- [ ] Every connection uses only the app's own relay for STUN and TURN, with fresh credentials
- [ ] With Hide my IP on, connections use relay-only transport; a test of the configuration covers both settings
- [ ] The user confirms with `getStats()` that a Call with Hide my IP on uses a relayed candidate pair against the development relay
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 03 — Voice controls

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-8, US-9, US-10

#### What To Build

A small Call settings panel holds the microphone mode, the push-to-talk key, the mute hotkey, the codec and Hide my IP, stored locally.
- **Voice activity:** the microphone level is measured with the Web Audio API, and the audio track stays on while it is above the threshold, closing 300 ms after it drops.
- **Push-to-talk:** the track is on only while the chosen key is held, detected globally through `uiohook-napi` (D74) behind the app's own interface.
- **Mute hotkey:** `Ctrl+Shift+M` by default, registered with Electron's global shortcuts, toggling mute from anywhere.

#### Affected repositories and layers

- newcord: `apps/desktop` (voice activity gate, push-to-talk service around `uiohook-napi`, global mute shortcut, Call settings panel, local settings, tests)

#### Acceptance Criteria

- [ ] `uiohook-napi` is installed only after the user approves its install script by name, and is used only through the app's own push-to-talk interface
- [ ] Unit tests cover the voice activity gate (threshold and 300 ms hold) and push-to-talk on key down and off on key up
- [ ] The settings panel changes mode, push-to-talk key, mute hotkey, codec and Hide my IP, and they survive a restart
- [ ] The user confirms push-to-talk works while a game or another app is in front, and the mute hotkey toggles from anywhere
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

### Step 04 — Screen sharing

**Status:** Implementing
**Execution type:** HITL
**Stories covered:** US-11, US-12, US-13, US-14

#### What To Build

A Participant clicks Share and picks a screen or a window from the app's own picker, which lists sources with thumbnails. The main process answers the window's screen-share request with that source, video only. The track's content hint is "detail". The chosen codec is listed first, with the others after it as fallback, and each viewer's bitrate is capped at 1.5 Mbps, at up to 1080p and 30 fps. While sharing, a visible indicator with a Stop button is shown. Viewers see the shared screen in the Call view.

#### Affected repositories and layers

- newcord: `apps/desktop` (main process display-media handler, source picker, codec preference and bitrate cap, sharing indicator, viewer display, tests)

#### Acceptance Criteria

- [ ] Sharing never captures audio
- [ ] Unit tests cover the codec ordering (chosen first, others kept) and the encoding parameters (1.5 Mbps cap)
- [ ] The sharing indicator with Stop shows whenever a share is running, and Stop ends it
- [ ] The user confirms that a shared window's text stays readable for a viewer, and that switching the codec setting changes the negotiated codec (checked with `getStats()`)
- [ ] `pnpm test`, `pnpm lint` and `pnpm typecheck` pass
