**Date:** 2026-10-14
**Branch type:** Feature
**Status:** Draft

**Repository:** newcord · **Issue:** [osLeonardo/newcord#4](https://github.com/osLeonardo/newcord/issues/4) · **Milestone:** M2 · Encrypted group chat · **Branch:** `feature/4-openmls-wasm-module`

## Problem

M2's encrypted Group chat needs MLS (D8): Group keys that change whenever **Members** join or leave, so a removed **Device** cannot read anything sent after its removal. The app is TypeScript on Electron, but the MLS implementation chosen is OpenMLS, a Rust library (D22). Until it runs inside the app's main process behind a small, tested API, neither the server work (#5) nor the desktop work (#6) can encrypt, decrypt or change a Group.

## Solution

A Rust crate in `packages/mls` wraps OpenMLS with cipher suite 1 (D38). It is compiled to WebAssembly with wasm-bindgen for Node.js and published inside the workspace as `@newcord/mls`. Its API covers what M2 needs:

- rebuild the Device's MLS signer from its M1 Ed25519 key, with a credential naming the Account's username and the Device's ID (D70)
- create **Key packages**, including a last-resort one
- create a Group, add and remove Devices, join from a welcome, leave
- encrypt and decrypt messages, and merge or drop the Device's own commit depending on whether the server accepts it
- save and restore the whole MLS state as one blob (D39)

The Electron main process loads the module; the interface never does. Rust tests and Vitest tests through the WebAssembly module prove the flows, including that a removed Device cannot read newer messages.

## User Stories

1. As a Member, I want my Chat messages encrypted so that only the Group's current Devices can read them, and the server holds only ciphertext.
2. As a Member, I want a Device removed from the Group to be unable to decrypt anything sent after its removal.
3. As a Member, I want a Device added to the Group to be able to read messages sent after it joined, and nothing from before.
4. As a Member, I want my Device's MLS identity tied to the same Ed25519 key it registered in M1, so that the key in the Key directory is the one that signs its MLS messages.
5. As a Member, I want every Device's credential to name its Account's username and Device ID (D70), so that my app can check commits against their declared changes (D41), count people for the 10-person limit, and group keys for safety numbers.
6. As a Member, I want people to be able to add my Device while it is offline, so that Invitations do not depend on me being online.
7. As a Member, I want a last-resort Key package always available, so that adding my Device never fails for lack of packages.
8. As a Member, I want to leave a Group by sending a removal request that the next Member online completes (D57).
9. As a Member whose commit lost the race for an epoch, I want to drop my pending commit and process the winning one, so that my Group state stays consistent with everyone else's.
10. As a Member, I want a Device that missed a change to be removed and re-added in one commit when asked to resync (D24).
11. As a Member, I want my whole MLS state saved as one blob after every change and restored on start (D39), so that a crash never leaves keys half-written.
12. As a Member, I want the AES used inside WebAssembly to be constant-time (security checklist, M2), so that timing does not leak keys.
13. As the developer, I want one command to build the module and one to run its Rust tests, and both covered by the root `test` script, so that the checks run locally before each merge (D68).
14. As the developer, I want the module loaded only in Electron's main process, so that keys never reach the interface.

## Implementation Decisions

### Interfaces and Contracts

The module's API, called only from the main process. Binary values are `Uint8Array`; structured results are plain objects.

| Function | Input | Output |
|---|---|---|
| `loadState` / `saveState` | state blob / — | — / state blob |
| `initIdentity` | Ed25519 private and public key (raw bytes), username, `deviceId` | — |
| `createKeyPackages` | count, whether one is last-resort | serialized Key packages |
| `createGroup` | Group ID (16 random bytes, from the caller) | — |
| `addMembers` / `removeMembers` | Key packages / Device identities | commit, and a welcome when adding |
| `updateMembers` | Key packages to add and Device identities to remove | one commit (and welcome) doing both |
| `leaveGroup` | Group ID | a removal request (MLS proposal) for this Device |
| `commitPendingProposals` | Group ID | commit completing pending removal requests |
| `joinFromWelcome` | welcome | Group ID |
| `encrypt` | Group ID, plaintext | MLS message |
| `processIncoming` | MLS message | for a message: plaintext and sender identity; for a commit: added and removed identities and the new epoch; for a proposal: what it requests |
| `mergePendingCommit` / `clearPendingCommit` | Group ID | — |

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Credential identity encoding (D70):** the UTF-8 text `<username>:<deviceId>`. Usernames cannot contain `:`; the server's Device IDs must not either. Anything else is rejected when parsed.
2. **Leaving and resync** need three functions the guide's table lacks. `leaveGroup` and `commitPendingProposals` implement D57, where the leaver requests and the next Member completes. `updateMembers` removes and re-adds a Device in one commit for resync (D24). `addMembers` and `removeMembers` stay as the guide names them.
3. **Welcomes carry the ratchet tree**, so a joining Device needs nothing from the server beyond the welcome.
4. **Every MLS message is encrypted**, commits included, as `06-message-formats.md` states ("Commits are encrypted like every other MLS message").
5. **Key package lifetime:** OpenMLS's default. The step that builds Key packages reports what that default is; if it is under 30 days (D24's wait), stop and ask.
6. **The state blob** holds everything: the storage provider's contents, the signer and the credential. `loadState` alone restores a working Device.
7. **Workspace package:** `packages/mls` is also the pnpm package `@newcord/mls`, with a build script that runs the Rust build and wasm-bindgen. The generated output is not committed. The root `test` script also runs the crate's Rust tests.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D8 MLS; D22 OpenMLS through WebAssembly; D38 cipher suite 1 (X25519, AES-128-GCM, SHA-256, Ed25519); D39 one state blob saved after every change; D57 leaving through a removal request; D70 username and device ID in the credential.
- Settings in `09-m2-build.md`: wasm-bindgen's command-line tool targeting Node.js, with its version exactly matching the wasm-bindgen crate; the `openmls_rust_crypto` provider; 20 Key packages plus one last-resort; 16-byte random Group IDs.
- The crate uses openmls, openmls_rust_crypto, openmls_basic_credential, openmls_memory_storage and wasm-bindgen, at the companion versions the openmls crate itself depends on, plus getrandom's JavaScript randomness feature for WebAssembly.

### Schema Changes

None in either database. The MLS state is an opaque blob; storing it is #6's job.

## Out of Scope

- Saving the blob to the app's database, `secure_delete`, the 10-person check and the declared-change check (D41): all in the desktop app (#6).
- Server handling of commits, welcomes, Key packages and ordering (#5).
- Removing a lost Device (#7).
- Call setup messages (M3), which reuse `encrypt` and `processIncoming` unchanged.

## Additional Notes

- Rust is not installed on the developer's machine. The toolchain (rustup, the `wasm32-unknown-unknown` target and the matching `wasm-bindgen-cli`) has to be installed first.
- getrandom 0.3's JavaScript backend needs its feature *and* a build configuration flag to be active on `wasm32-unknown-unknown`. Check the version in use.
- wasm-bindgen's Node.js output loads its `.wasm` file from beside its JavaScript. Bundling it into the main process changes that path, so the module must stay external to the bundle or have its file copied next to it. Packaging is M5's concern, but the development build must work now.
- Depends on #3 for the M1 identity key. The crate and its tests can be built before #3 lands.

### Step 02 — Identity, Key packages and the state blob

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-4, US-5, US-6, US-7, US-11

#### What To Build

A Device's MLS identity is rebuilt from its M1 Ed25519 key: `initIdentity` takes the raw private and public key bytes, the username and the `deviceId`, and creates a basic credential whose identity is `<username>:<deviceId>` (D70). `createKeyPackages` returns the requested number of serialized Key packages, optionally including a last-resort one. `saveState` exports everything — storage contents, signer and credential — as one blob, and `loadState` restores a working Device from it.

Not included: Groups and messages (Step 03).

#### Affected repositories and layers

- newcord: `packages/mls` (identity, Key packages, state blob, Rust tests, Vitest tests through the module)

#### Acceptance Criteria

- [ ] A key pair generated by Node.js's crypto, passed to `initIdentity` as raw bytes, yields a signer whose public key equals the Node.js public key (tested through the module)
- [ ] The credential identity is exactly `<username>:<deviceId>` in UTF-8; parsing rejects identities without exactly one `:` or with an invalid username
- [ ] `createKeyPackages(n, lastResort)` returns `n` Key packages for cipher suite 1, the last marked last-resort when requested
- [ ] The Key packages' lifetime is reported in the step's summary; if OpenMLS's default is under 30 days, the step stops and asks the user
- [ ] After `saveState`, a fresh module instance given the blob through `loadState` can create Key packages with the same credential and signer, without calling `initIdentity`
- [ ] Functions called before `initIdentity` or `loadState` fail with a clear error instead of panicking
- [ ] Rust tests and Vitest tests cover each rule above

#### Blockers

- [Step 01 — Toolchain, crate and Node.js build](#step-01--toolchain-crate-and-nodejs-build)

#### Implementation Notes

- openmls_basic_credential can rebuild a signature key pair from raw bytes; check which private-key form it expects for Ed25519 (the 32-byte seed or a longer form) at the version in use.
- A Rust panic in WebAssembly aborts the module instance; convert errors into JavaScript exceptions at the boundary.

### Step 03 — Groups and messages

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-3, US-5, US-9

#### What To Build

Devices can form a Group and talk. The full set of functions arrives here:
- `createGroup` starts a Group with the caller as its only member, using the caller's 16-byte ID.
- `addMembers` returns a commit and a welcome. The welcome carries the ratchet tree, and `joinFromWelcome` lets the added Device join from it.
- `encrypt` produces MLS messages, and every message is encrypted, commits included.
- `processIncoming` decrypts messages, returning the plaintext and the sender's identity, and applies commits, returning the added and removed identities and the new epoch.
- `mergePendingCommit` finalises the caller's own commit, and `clearPendingCommit` drops it.

Not included: removing, leaving and resync (Step 04).

#### Affected repositories and layers

- newcord: `packages/mls` (Group creation, adding, joining, encryption, processing, pending commits, tests)

#### Acceptance Criteria

- [ ] Two Devices: A creates a Group, adds B, B joins from the welcome alone, and messages encrypted by either are decrypted by the other with the right sender identity
- [ ] Three Devices: C added later reads messages sent after it joined, and cannot decrypt a message sent before
- [ ] `processIncoming` on a commit returns the identities it added and the new epoch
- [ ] Commits and application messages are both produced in encrypted form
- [ ] Race: A and B each create a commit for the same epoch; B drops its own with `clearPendingCommit`, applies A's, and both Groups end in the same epoch and keep exchanging messages
- [ ] `mergePendingCommit` after acceptance moves the creator to the new epoch
- [ ] The state blob saved mid-conversation and restored into a new instance keeps decrypting new messages
- [ ] Rust tests and Vitest tests cover each flow above

#### Blockers

- [Step 02 — Identity, Key packages and the state blob](#step-02--identity-key-packages-and-the-state-blob)

### Step 04 — Removing, leaving and resync

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-2, US-8, US-10

#### What To Build

Devices can leave a Group or be taken out of it:
- `removeMembers` removes Devices by identity.
- `leaveGroup` creates the caller's own removal request, and `commitPendingProposals` lets another Member complete it (D57).
- `updateMembers` removes and re-adds a Device in one commit, with a welcome, for resync (D24).

`processIncoming` reports proposals and the identities a commit removed.

Not included: anything in the desktop app (#6).

#### Affected repositories and layers

- newcord: `packages/mls` (removal, leaving, combined commits, tests)

#### Acceptance Criteria

- [ ] After A removes C, C cannot decrypt any message sent after the removal, while A and B continue
- [ ] B calls `leaveGroup`; A receives the request through `processIncoming`, completes it with `commitPendingProposals`, and B cannot decrypt anything afterwards
- [ ] `updateMembers` removing and re-adding the same Device in one commit lets that Device join again from the welcome and read new messages, while its old state cannot read them
- [ ] `processIncoming` on a removal commit returns the removed identities
- [ ] Rust tests and Vitest tests cover each flow above
