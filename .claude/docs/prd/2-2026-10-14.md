## Problem

After the scaffold (#1) the server only answers `/health`. Nobody can create an **Account**, no **Device** can prove who it is, and there is no live connection to tell anyone who is online. The desktop app (#3) has nothing to sign up, log in or connect to, and M1's gate — two computers seeing each other online — cannot be reached.

## Solution

The server gains everything an Account and its Devices need in M1:

- Sign-up, login, token refresh and logout over HTTP, with each Device identified by its identity key (D59) and each key belonging to one Account only (D60).
- Short-lived access tokens (HS256 JWT, 15 minutes) and rotating refresh tokens (30 days) whose reuse logs the Device out (D62).
- Password change from a logged-in Device and recovery with a **Recovery code** (D55), both cutting off other sessions at once (D66).
- The **Key directory**, readable only by logged-in Accounts (D64).
- A WebSocket hub at `/ws`: a `hello` **Envelope** within 5 seconds, then presence updates to every connected client, with sockets closed whenever their session ends.
- Every request and Envelope validated against shared TypeBox schemas with unknown fields rejected, every limit from the Settings table enforced, and no secret ever written to a log.

## User Stories

1. As a new user, I want to sign up with a username and password from my Device, so that I have an Account and my Device is logged in.
2. As a new user, I want to receive a Recovery code exactly once at sign-up, so that I can reset my password if I forget it.
3. As a user, I want sign-up to reject usernames outside 3–32 lowercase letters, digits and underscores, and passwords shorter than 12 characters, so that names are easy to type and passwords are hard to guess.
4. As a user, I want sign-up to tell me when a username is already taken, so that I can choose another.
5. As a user, I want to log in from a Device with my username, password and the Device's identity key, so that the server recognises this Device or adds it to my Account the first time (D59).
6. As a user, I want logging out and back in on the same Device to keep it the same Device, so that my Account does not fill up with duplicates.
7. As a user, I want the server to refuse an identity key that already belongs to another Account, so that nobody can link two Accounts through the Key directory (D60).
8. As a user, I want my Device to swap its refresh token for new tokens without asking for my password, so that I stay logged in for up to 30 days of use.
9. As a user whose refresh token was copied, I want the server to log my Device out as soon as an already-used token is presented, so that a thief's copy stops working (D62).
10. As a user, I want logging out to end my Device's session immediately, including its open WebSocket.
11. As a user on a logged-in Device, I want to change my password without the old one (D55), so that I can secure my Account from any Device I hold.
12. As a user whose laptop was stolen, I want changing my password to cut off every other Device of mine at once, including their open WebSockets (D66).
13. As a user who forgot my password, I want to set a new one with my username and Recovery code, which logs out every Device of mine at once and gives me a new code (D55, D66).
14. As a user, I want a used Recovery code to stop working, so that a code seen once cannot be used again.
15. As a logged-in user, I want to look up another Account's Device identity keys, so that later milestones can add people and compare safety numbers.
16. As a user, I want the Key directory closed to anyone who is not logged in, so that strangers cannot list usernames or Device counts (D64).
17. As a user, I want my Device's live connection to authenticate with a `hello` Envelope rather than a URL, so that tokens never end up in logs.
18. As a user, I want to see which Accounts are online and be told when that changes, so that the M1 "online now" list works.
19. As a user, I want a live connection whose session has ended — expired, logged out, password changed — to be closed by the server, so that a lost Device does not keep listening.
20. As the operator, I want login, sign-up, refresh, password change, recovery and Key directory lookups rate-limited, so that guessing and floods are slowed down.
21. As the operator, I want request bodies and WebSocket messages capped at 64 KiB, and anything with unknown fields rejected, so that malformed input never reaches the handlers.
22. As the operator, I want logs never to contain passwords, tokens, Recovery codes or Payloads, so that a leaked log leaks no secrets.
23. As the operator, I want the server to refuse to start without a JWT secret of at least 32 random bytes from the environment, so that a weak or committed secret cannot happen by accident.

## Implementation Decisions

### Interfaces and Contracts

All bodies are JSON. Binary values travel in base64 (D30). Every request schema lives in `@newcord/shared` and rejects unknown fields.

| Route | Auth | Request | Success response |
|---|---|---|---|
| `POST /register` | none | `username`, `password`, `identityKey` | `201`: `accessToken`, `refreshToken`, `deviceId`, `recoveryCode` |
| `POST /login` | none | `username`, `password`, `identityKey` | `200`: `accessToken`, `refreshToken`, `deviceId` |
| `POST /refresh` | none | `refreshToken` | `200`: `accessToken`, `refreshToken` |
| `POST /logout` | access token | none | `204` |
| `POST /password/change` | access token | `newPassword` | `204` |
| `POST /password/recover` | none | `username`, `recoveryCode`, `newPassword` | `200`: `recoveryCode` |
| `GET /users/:username/keys` | access token | none | `200`: the identity keys of that Account's Devices |

- Access tokens travel as `Authorization: Bearer <JWT>`. The JWT is HS256 only, expires after 15 minutes and names the Account and the Device.
- Errors never distinguish "no such username" from "wrong password" at login. Sign-up does reveal a taken username (`409`), as accepted in D64's reasoning.
- WebSocket at `/ws`: every Envelope carries a protocol version and a type. The client's first Envelope is `hello` with the access token; the server sends presence Envelopes: a snapshot of online Accounts after `hello`, then online/offline changes. The server closes a socket with distinct application close codes for "authentication failed or timed out" and "session ended", so the app (#3) can tell a logout from a network drop.

**Filled in during this spec (not stated in the guide) — confirm at Gate 1:**

1. **Identity key format:** the raw 32-byte Ed25519 public key, base64 — the form OpenMLS needs in M2 — not Node's default SPKI export. The server rejects anything that does not decode to 32 bytes.
2. **Refresh tokens:** 32 random bytes (256 bits), base64url, stored as their SHA-256 hash.
3. **Logout** is authenticated with the access token and deletes all of that Device's refresh tokens.
4. **Recovery** returns only the new Recovery code, not tokens; the app then logs in with the new password.
5. **Presence is per Account:** an Account is online while at least one of its Devices has an authenticated socket, so logging out one of two Devices does not mark the Account offline.
6. **The 15-minute check** treats a Device as still logged in only if it has an unused, unexpired refresh token.

### Architectural Decisions (ADR)

This repository records decisions in `docs/guide/03-decisions.md`, not ADRs.

- D7, D35 Argon2id (19 MiB, 2 iterations, 1 thread); D34 better-sqlite3; D36 TypeBox; D37–D37c HS256 JWT plus refresh tokens; D55 password change without the old password, and recovery codes; D59 login sends the identity key; D60 one Account per identity key; D61 no proof of possession; D62 reuse detection; D64 logged-in Key directory; D66 sockets closed on password change and recovery.
- Every value in the Settings table of `08-m1-build.md` applies as written: lifetimes, Argon2id cost, username and password rules, every rate limit, the 64 KiB limits, the 5-second `hello` deadline, the Crockford Base32 Recovery code (24 characters, about 120 bits, shown in groups of four).
- Presence goes to every connected client in M1; M2 narrows it to Group Members (#5).
- Rate limits are kept in memory: there is one server process (D52).

### Schema Changes

New SQLite tables, as in `08-m1-build.md` step 2:

- `users` (`id`, `username` unique, `password_hash`, `recovery_hash`, `created_at`)
- `devices` (`id` server-generated, `user_id`, `identity_key` unique across all Accounts, `created_at`)
- `refresh_tokens` (`token_hash` primary key, `device_id`, `expires_at`, `used_at`)

## Out of Scope

- The desktop app's use of these routes, its identity key, local database and screens (#3).
- Groups, Invitations, Key packages, the message queue, and narrowing presence and the Key directory to Group Members (M2, #5).
- Removing a lost Device (#7) and deleting an Account (D67, out of scope for v1).
- TLS: development runs on plain http to the local machine; production TLS is nginx's job (D53, #14).
- Any CI workflow (D68).

## Additional Notes

- `better-sqlite3` and `argon2` compile native code and must be approved by name (`pnpm approve-builds better-sqlite3 argon2`). If either has no prebuilt binary for Node.js 26 and fails to build, stop and report — do not change the Node.js version (`07-m1-setup.md` Settings).
- The guide imports TypeBox from the `typebox` package together with `@fastify/type-provider-typebox`. If the installed versions do not work together, stop and report with options rather than switching packages silently.
- Fastify's validator removes unknown properties by default instead of rejecting them; the checklist requires rejecting them.
- Per-username rate limits (login, recovery) need the parsed body, which is not available at the point where rate limiting usually runs.
- Depends on #1.

## Steps

### Step 01 — Sign-up end to end

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-1, US-2, US-3, US-4, US-20, US-21, US-22, US-23

#### What To Build

A new user's Device can call `POST /register` and get an Account, a Device, an access token, a refresh token, its `deviceId` and a one-time Recovery code. Behind it: the request schemas in `@newcord/shared`, the three tables created on start, Argon2id password and Recovery code hashing, JWT and refresh-token issuance, and the server-wide protections every later route relies on — the 64 KiB body limit, rejection of unknown fields, log redaction and the startup check on the JWT secret. The sign-up rate limit applies.

Not included: login, refresh, logout, access-token checks on routes (Step 02), the WebSocket (Step 03).

#### Affected repositories and layers

- newcord: `packages/shared` (request and response schemas), `apps/server` (configuration, database and migrations, password and token services, the register route, tests)

#### Acceptance Criteria

- [ ] `better-sqlite3`, `argon2`, `@fastify/jwt`, `@fastify/rate-limit`, `typebox` and `@fastify/type-provider-typebox` are server dependencies; `typebox` is a dependency of `@newcord/shared`; `allowBuilds` gains only `better-sqlite3` and `argon2`
- [ ] The server refuses to start, with a clear message, when the JWT secret from the environment is missing or shorter than 32 bytes
- [ ] On start, the server creates the `users`, `devices` and `refresh_tokens` tables as specified in the PRD's Schema Changes if they do not exist, with foreign keys enforced
- [ ] `POST /register` with a valid request returns 201 with `accessToken`, `refreshToken`, `deviceId` and `recoveryCode`, and creates one user and one device row
- [ ] The returned Recovery code is 24 characters of Crockford Base32; the database holds only its Argon2id hash
- [ ] The password is stored only as an Argon2id hash with 19 MiB of memory, 2 iterations and 1 thread
- [ ] The refresh token is 32 random bytes in base64url, and the database holds only its SHA-256 hash with an expiry 30 days ahead
- [ ] The access token is an HS256 JWT expiring after 15 minutes that names the Account and the Device
- [ ] Rejected with 400: usernames outside `^[a-z0-9_]{3,32}$`, passwords shorter than 12 or longer than 256 characters, an `identityKey` that does not decode to exactly 32 bytes, and any request with a field not in the schema
- [ ] A taken username returns 409; an identity key already registered returns an error and creates nothing
- [ ] A request body over 64 KiB is rejected without reaching the handler
- [ ] The sixth sign-up from one IP address within an hour is rejected with 429
- [ ] A test asserts that the log output of a sign-up contains neither the password, the tokens nor the Recovery code
- [ ] All tests run against an in-memory database, and `pnpm test`, `pnpm lint` and `pnpm typecheck` pass

#### Blockers

#### Implementation Notes

- Fastify's built-in validator strips unknown properties by default (`removeAdditional`); turn that off so schemas with `additionalProperties: false` reject them.
- 256 is a multiple of 32, so mapping each random byte to a Crockford symbol with `byte & 31` is unbiased.
- `Buffer.from(x, "base64")` silently ignores invalid characters; validate the base64 text itself before checking the decoded length.
- Keep the schemas and the Crockford alphabet in `@newcord/shared`, since the desktop app (#3) normalises typed-in codes with the same alphabet.
- Make Device IDs random (for example 16 random bytes in base64url) and never containing `:`. M2 writes them into MLS credentials as `<username>:<deviceId>` (D70, #4's PRD).
- If `better-sqlite3` or `argon2` fails to install on Node.js 26, or `typebox` and `@fastify/type-provider-typebox` do not work together, stop and report with options.

### Step 02 — Login, refresh and logout

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-5, US-6, US-7, US-8, US-9, US-10, US-20

#### What To Build

A Device can log in with username, password and identity key and is matched to its existing Device or added as a new one (D59); a key owned by another Account is refused (D60). A Device can swap its refresh token for new tokens, and presenting an already-used token deletes all of that Device's refresh tokens (D62). A logged-in Device can log out, deleting all of its refresh tokens. Access tokens are checked on authenticated routes, accepting HS256 only. Login and refresh are rate-limited.

Not included: closing WebSockets on logout and on reuse (Step 03), password change and recovery (Step 04), the Key directory (Step 05).

#### Affected repositories and layers

- newcord: `packages/shared` (login, refresh and response schemas), `apps/server` (access-token check, login, refresh and logout routes, token service, cleanup of used and expired refresh tokens, tests)

#### Acceptance Criteria

- [ ] `POST /login` with the correct password and a key this Account already has returns 200 with the existing `deviceId`; with a new key it creates a Device and returns its new `deviceId`
- [ ] `POST /login` with a key registered to another Account is refused and creates nothing
- [ ] A wrong password and an unknown username return the same status and body
- [ ] The sixth login attempt within a minute is rejected with 429, both for one username from several IP addresses and for one IP address across usernames
- [ ] `POST /refresh` with a valid token returns new tokens and marks the old token as used rather than deleting it
- [ ] Presenting a used refresh token deletes every refresh token of that Device, so the newest one stops working too
- [ ] Expired or unknown refresh tokens are rejected
- [ ] The 21st refresh from one IP address within a minute is rejected with 429
- [ ] `POST /logout` with a valid access token returns 204 and deletes every refresh token of that Device; without one it returns 401
- [ ] Access tokens signed with any algorithm other than HS256, with a wrong secret, or expired, are rejected
- [ ] Used and expired refresh-token rows are deleted after they expire, without a request having to trigger it
- [ ] Tests cover each rule above, including logging out and back in on the same Device keeping the same `deviceId`

#### Blockers

- [Step 01 — Sign-up end to end](#step-01--sign-up-end-to-end)

#### Implementation Notes

- Mark the old refresh token as used and insert the new one in one transaction, so two simultaneous refreshes with the same token cannot both succeed.
- For an unknown username, still run an Argon2id verification against a fixed dummy hash, so response time does not reveal whether the username exists.
- Per-username limits need the parsed body; run that limit after body parsing rather than at the start of the request.
- Configure the JWT verifier with an explicit allow-list containing only HS256.

### Step 03 — WebSocket hub and presence

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-10, US-17, US-18, US-19, US-21

#### What To Build

A Device opens `/ws`, sends a `hello` Envelope with its access token within 5 seconds, and from then on receives presence: a snapshot of the online Accounts, then changes as Accounts come online or go offline. An Account is online while any of its Devices holds an authenticated socket. The server closes sockets whose session has ended: at logout, when a used refresh token is presented, and at the 15-minute check when the Device no longer has an unused, unexpired refresh token. It uses distinct application close codes for "authentication failed or timed out" and "session ended". Envelopes are validated against shared schemas and capped at 64 KiB.

Not included: password change and recovery closing sockets (Step 04), Groups and narrowing presence (M2).

#### Affected repositories and layers

- newcord: `packages/shared` (Envelope schemas for `hello` and presence, the protocol version, close codes), `apps/server` (WebSocket route, registry of authenticated sockets per Device, presence, periodic session check, hooks from logout and refresh reuse, tests)

#### Acceptance Criteria

- [ ] Every Envelope carries a protocol version and a type, defined in `@newcord/shared` along with the close codes
- [ ] A socket that sends no valid `hello` within 5 seconds is closed with the authentication close code
- [ ] `hello` with an expired, forged or non-HS256 token closes the socket with the authentication close code
- [ ] After a valid `hello`, the socket receives a presence snapshot listing the online Accounts by username
- [ ] When an Account's first Device connects, every other authenticated socket receives an "online" change; when its last Device disconnects, an "offline" change
- [ ] Logging out one of two connected Devices of the same Account closes only that Device's sockets and does not send "offline"
- [ ] `POST /logout` closes that Device's sockets at once with the session-ended close code
- [ ] Presenting a used refresh token closes that Device's sockets at once with the session-ended close code
- [ ] Every 15 minutes, sockets of Devices with no unused, unexpired refresh token are closed with the session-ended close code
- [ ] An Envelope over 64 KiB, with an unknown type, or with a field not in its schema is rejected
- [ ] The token sent in `hello` never appears in the log output
- [ ] Tests cover each rule above

#### Blockers

- [Step 02 — Login, refresh and logout](#step-02--login-refresh-and-logout)

#### Implementation Notes

- `@fastify/websocket` can inject WebSocket connections in tests without opening a port; check the installed version's documentation.
- The socket's message size limit is set on the underlying WebSocket server options, separately from the HTTP body limit.
- Keep the socket registry behind a small interface (close all sockets of a Device, close all sockets of an Account), because Step 04 and M2 both reuse it.

### Step 04 — Password change and recovery

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-11, US-12, US-13, US-14, US-20

#### What To Build

A logged-in Device can set a new password without the old one (D55). That deletes the refresh tokens of the Account's other Devices and closes their sockets at once (D66), while the Device that made the change stays logged in. Anyone with the username and a valid Recovery code can set a new password. That deletes every refresh token of the Account, closes all its sockets (D66), replaces the Recovery code and returns the new one once. The old code stops working. Both routes are rate-limited.

Not included: any change to login or the WebSocket beyond using the socket registry from Step 03.

#### Affected repositories and layers

- newcord: `packages/shared` (password change and recovery schemas, Recovery code normalisation), `apps/server` (both routes, tests)

#### Acceptance Criteria

- [ ] `POST /password/change` with a valid access token and a valid new password returns 204 and stores the new Argon2id hash
- [ ] After a change, the other Devices' refresh tokens are deleted and their sockets closed with the session-ended close code; the calling Device's token and socket keep working
- [ ] `POST /password/change` without an access token returns 401; a new password breaking the length rules returns 400
- [ ] The sixth password change by one Account within an hour is rejected with 429
- [ ] `POST /password/recover` with the right username and code returns 200 with a new 24-character Recovery code, stores the new password and code hashes, deletes every refresh token of the Account and closes all its sockets
- [ ] Recovery accepts the code in any letter case and with dashes or spaces, and reads O as 0 and I or L as 1
- [ ] After a successful recovery, the old code is refused
- [ ] A wrong code and an unknown username return the same status and body
- [ ] The sixth recovery attempt within an hour is rejected with 429, both per username and per IP address
- [ ] Neither the new password nor either Recovery code appears in the log output
- [ ] Tests cover each rule above

#### Blockers

- [Step 03 — WebSocket hub and presence](#step-03--websocket-hub-and-presence)

#### Implementation Notes

- As at login, verify against a fixed dummy hash for an unknown username, so timing does not reveal whether it exists.
- Update the password hash, the Recovery code hash and the deleted tokens in one transaction, then close the sockets.

### Step 05 — Key directory

**Status:** Implementing
**Execution type:** AFK
**Stories covered:** US-15, US-16, US-20

#### What To Build

A logged-in Device can look up `GET /users/:username/keys` and receive the identity keys of that Account's Devices (D64). Requests without a valid access token are refused, and each Account is limited to 60 lookups per minute.

Not included: narrowing lookups to Accounts that share a Group or a pending Invitation (M2, #5).

#### Affected repositories and layers

- newcord: `packages/shared` (response schema), `apps/server` (route, tests)

#### Acceptance Criteria

- [ ] With a valid access token, the route returns 200 with the base64 identity keys of every Device of that Account
- [ ] An unknown username returns 404
- [ ] A username not matching the username rules returns 400
- [ ] Without a valid access token the route returns 401
- [ ] The 61st lookup by one Account within a minute is rejected with 429
- [ ] Tests cover each rule above

#### Blockers

- [Step 02 — Login, refresh and logout](#step-02--login-refresh-and-logout)

#### Implementation Notes

- Key the rate limit on the Account from the verified access token, not on the IP address.
