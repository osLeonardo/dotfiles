name: agent-implement-prd
allowed-tools: Read, Glob, Agent, SendMessage
description: Reads a PRD and orchestrates parallel execution of its steps using subagents. Use when the user wants to execute multiple PRD steps at once, or wants to delegate the whole execution of a PRD to the agent.
---

Reads a PRD generated by `spec-task`, identifies which steps can run in parallel (no blockers between them) and delegates each one to an independent `step-agent` subagent.

The developer approves the execution plan at the start and the result at the end. In between, execution runs on its own: a group only moves on to the next once the `verify` of all its steps passes, and the developer is only called when a subagent stops at a gate.

---

## Prerequisites

| Field | Source | If missing |
|---|---|---|
| PRD file | User argument | Show the list of PRDs available in `.claude/docs/prd/` |
| Global execution mode | User instruction | Assume HITL |

---

## Step 1 — Read the PRD

Read the PRD file in full. Extract:

- The issue number
- The list of steps with: number, title, status, execution type (AFK/HITL), declared blockers

Consider steps with `Status: Pending` for execution. `Finished` steps appear in the plan only as already finished.

A step in `Implementing` comes from an earlier, interrupted execution, and its code may be half done. Do not ignore it: show it separately in the plan and ask the developer whether it goes back into the execution or stays out. As long as it is not `Finished`, no step that depends on it enters a group.

---

## Step 2 — Build the execution plan

Identify the **execution groups**: sets of steps that can run in parallel because they have no blockers between them (or all their blockers are already `Finished`).

Present it to the user before executing anything:

```
Execution plan — issue #<number>

Group 1 (parallel):
  [01] <Title> — AFK
  [03] <Title> — AFK

Group 2 (waits on Group 1):
  [02] <Title> — ⚠ HITL
  [04] <Title> — AFK

Already finished steps (ignored):
  [00] <Title>

Steps in Implementing (interrupted earlier execution — resume or leave out?):
  [05] <Title>
```

Wait for explicit confirmation before proceeding. The user may adjust the order or drop steps from the plan at this point. **This is the last approval before the code review gate:** once the plan is approved, the groups run in sequence without further confirmation.

---

## Step 3 — Execute group by group

For each group, in the order defined in the plan:

### 3a — Dispatch subagents in parallel

For each step in the group, invoke the `step-agent` subagent passing:
- The PRD path
- The step number and title
- The issue number
- The global execution mode, if the user set one (it overrides the step's `Execution type`)

For an `Implementing` step the developer chose to resume, say in the message that it was interrupted in an earlier execution and that the `step-agent` must start from the current state of the code, without redoing what already exists.

Steps in the same group are dispatched **simultaneously** — do not wait for one to finish before starting the next one in the same group.

**Store the identifier of each dispatched subagent**, associated with its step. You will need it to **continue that same subagent** — when relaying a gate decision (3b) and when requesting fixes (Steps 5 and 6).

### 3b — Handle the returns

**GATE — requires a developer decision:**

```
GATE: <Architectural | Verify>
STEP: <number> — <title>
MESSAGE: <context for the decision>
```

On receiving a GATE:
1. Show it to the user exactly as received
2. Wait for the decision
3. **Continue the same subagent** that raised the gate (by the identifier stored in 3a), sending the developer's decision — **do not** dispatch a new subagent. Continuing preserves the context it has already built up, avoiding rework and divergence. The subagent resumes where it stopped and will raise another gate or return `DONE`.
4. The other subagents in the group keep running normally

Gates **always** reach the developer. No step setting dismisses them.

**DONE — step finished:**

```
DONE
STEP: <number> — <title>
VERIFY: ...
CHANGED FILES: ...
TESTS: ...
OUT OF SCOPE: ...
SUMMARY: ...
```

On receiving DONE:
1. Check `VERIFY`: every repository must be `TESTS_PASSED` or `NO_TESTS_APPLICABLE`. If the block is missing or any repository comes back with another code, **the step is not done** — treat it as `GATE: Verify` and take it to the developer.
2. Store the `CHANGED FILES` associated with the step — you will need them to route findings in Step 5
3. Record it in the status table (see Step 4)

### 3c — Move to the next group

When **all** steps in the current group are `DONE` with a valid `VERIFY`, start the next group **immediately, without asking the developer** — the plan approval in Step 2 already covers it. Report the advance only in the status table.

A step stopped at a gate holds the whole group: the next group only starts after the developer decides and that step reaches `DONE`.

---

## Step 4 — Maintain the status table

Throughout the execution, maintain and display an updated status table after each event (gate received, step finished, group started, review started):

```
Execution status — issue #<number>

[✓] Step 01 — <Title> (done, verify ok)
[⏳] Step 03 — <Title> (in progress)
[⏸] Step 02 — <Title> (waiting on gate: Verify)
[—] Step 04 — <Title> (waits on Group 1)
```

---

## Step 5 — Automatic review and fixes

When all steps are `DONE`, **without consulting the developer**:

1. Invoke the `code-reviewer` subagent (`{root}/.claude/agents/code-reviewer.md`) passing: the PRD path, the consolidated list of files changed by all steps, the affected repositories and the paths of the applicable pattern docs (`coding-rules.md`, `testing-rules.md` and the `*-patterns.md`).
2. IF the verdict is `nothing to report` → go straight to Step 6.
3. Split the `BLOCKER` and `WARNING` findings by step, using the file cited in each: the owning step is the one that has that file in its `CHANGED FILES`; a file no step changed goes to the step in the same repository. A finding that cannot be attributed to a step is not sent — it goes to the gate as unfixed.
4. **Continue the `step-agent` that owns each set of findings** (by the identifier stored in 3a), sending the findings in full. Steps with no findings are not called. Dispatches to different steps run in parallel.
5. Each subagent returns `CORRECTION` (or a GATE — handle it as in 3b). Check the return's `VERIFY` as in 3b.

`NOTE` findings are not sent for fixing — they go straight to the gate. The review runs only once: the `code-reviewer` is not invoked again after the fixes, because the developer sees the result in the next step.

---

## Step 6 — Developer code review gate

Present, in this order:

```
Execution complete — issue #<number>

Steps implemented: N
Verify per repository: <repository: code>

Review (code-reviewer), in full — BLOCKER first, ending with its VERDICT line:
  <reviewer's return>

Automatic fixes:
  <per step: each finding FIXED with what changed, and each DISPUTED with the reason>
  <findings that could not be attributed to a step>

Tests per criterion:
  <per step: each test and the AC-N.M criterion it covers>

Out-of-scope behavior found by the steps:
  <list, or "none">

Changed files:
  - <consolidated list, no duplicates>
```

Wait for the developer's decision:
- **Approved** → suggest the next steps: `document-task` to generate the issue closeout text / PR body, and `git-process` to run the tests, push and open the Pull Request
- **Adjustments** → send each adjustment to the `step-agent` that owns it, as in Step 5, and come back to this gate with the result

---

## Rules

- Never start a group with pending blockers
- Never move to the next group while steps from the current one are still running, stopped at a gate or without a valid `VERIFY`
- Between plan approval and the code review gate, do not ask the developer for confirmation — they are only called when a subagent stops at a gate
- Gates always reach the developer — never make the decision on the user's behalf
- When relaying a gate decision or requesting a fix, **continue the same subagent** — never dispatch a new one for a step that already has a subagent
- Gates received from any subagent pause **only that subagent** — the others continue
- Do not run any git command
